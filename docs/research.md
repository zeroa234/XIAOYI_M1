## 包内说明核对

使用已安装的 Python `zipfile`、`pypdf` 在内存中读取说明，不修改源文件。

- 3.2-cn 的本次变更为修复 iOS 11 预览；历史 3.0 说明列出 AF 速度提升，3.1 列出已知 bug/稳定性修正。
- 12-40mm 1.1 说明是修复个别情况下画面异常抖动。
- 42.5mm 1.1 说明是修复暗调被摄体个别情况下不能合焦。
- 这些说明不能证明用户当前的随机卡死和对焦慢已被修复或由同一原因导致。

## 已核实设备状态

只读 USB/文件系统检查：设备为 `YI YI-M1 USB Device`；E 盘可读，exFAT，总容量 63,831,015,424 字节，可用 15,885,926,400 字节。仅列举卡根目录，未读取照片内容。普通沙箱中设备读取受限；经批准的只读设备检查成功。

用户报告使用闪迪 64 GB 卡，资料已有备份，卡死触发随机。尚无完整复现步骤、日志、供电状态或替换卡对照，不能据此诊断为算法或 CPU 性能问题。

后续补充：用户表示多张存储卡均复现，认为供电正常；记得 3.1 较稳定。调查主线调整为版本回归、参数持久化、模式切换和界面响应，不继续要求轮换 SD 卡。对“所有 M1 都有问题”的描述不作总体统计结论。

最新复测更正：用户表示“好像有记忆”，普遍丢失参数的初步判断撤回。随后确认 M 档、固定 ISO、闪光关闭时，调节光圈、ISO、快门会改变成片亮度，照片与视频取景亮度均不变，小蚁与松下镜头均复现。

测试期间用户报告完全挂死 5 次，电源开关无效、须拔电池恢复，并称多种操作都可能触发。已停止要求反复测试，优先调查严重系统无响应，曝光预览作为明确的后续功能修复目标；不能把挂死直接诊断成性能优化、CPU 负载或某种死锁。

用户授权使用 piagent 后，启动两个并行离线审计，分别检查压缩验证与故障诊断接口。后续用户确认可以回退，并重申交付应基于 3.2 保留功能，同时优化性能/稳定性和实现曝光预览；3.1 只作对照及恢复备用。

针对曝光预览的检索再次取得 Zack 一手评测的可读检索正文，作者明确限定测试版本为 1.02-int 与 2.0-int，并明确描述没有随曝光变化的取景预览。这是历史实测，不能直接认定所有后续版本行为相同。未用景深预览、连续 AF 或取景流是否存在来代替亮度曝光模拟。

## 验证顺序

1. 保留官方输入，记录 SHA-256、固件分段和校验情况。
2. 审阅第三方工具及依赖后，仅对本地副本拆包和分析。
3. 区分正常校验、拆包成功与运行正确；未经验证的重打包结果只用于离线实验。
4. 利用系统现成工具只读检查 SD 文件系统；不把健康的文件系统等同于卡、供电或硬件完全正常。
5. 依据复现条件决定是否需要无线状态采集或硬件调试，定位后再设计修补。

## 候选机器码分析与隔离执行阶段

按用户最新要求继续以 3.2-cn 为基线。现成工具选择为 Ghidra 12.2（反编译）、Capstone（指令复核）、Unicorn 2.1.4（隔离执行）；Java、工具、缓存和分析数据库均存放本项目。自写部分仅负责固定输入、装载、运行现成工具和收集结果。

Ghidra 首轮分析成功，记录用时 130 秒；重点导出最多 60 个函数。几个 12 字节共享助手对寄存器或栈有普通 ABI 未表达的影响，经 Capstone 核对后仅在数据库中标记 inline，再导出 C 视图。对未恢复的间接分派继续保留不确定性，没有把反编译异常当作固件错误。

复用现有远程控制项目中的命令表越界线索，在 CN 候选上独立找到 45 项/360 字节的表和以 360 为条目数的搜索循环。106 个 ARM 隔离执行用例验证：模拟器内收紧上限保持所有已知命令结果，并消除未知命令时第一笔表外读取。没有输出改写镜像，尚不能证明它导致用户日常卡死，也未解决曝光模拟。阶段状态见 `reports/status-2026-10-26.md`。
