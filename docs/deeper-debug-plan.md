# 进一步取得 M1 底层证据的执行路线

日期：2026-10-26。目标仍是保留 3.2-cn 功能、定位卡顿/完全挂死、实现取景曝光模拟。本文件说明如何补足当前证据，不表示已发现 M1 的可用调试口。

## 起点与尚未核实的条件

- 已有：官方输入、候选 ARM 机器码、分段/装载表、部分实际指令和 RAM 单元的读写线索。
- 尚缺：真机运行内存对照、运行事件时序、挂死时的处理器/任务现场、完整恢复方法。
- 本机 Windows USB 枚举表现为 SD 大容量存储；没有已验证的 PTP、USB 调试或内存读取接口。
- 固件有 ARM926 相关启动线索，**尚无已核实的主板芯片型号、核心分工、调试焊盘、IO 电平或调试解锁状态**。不能仅据这些字符串直接编写适用本机的 JTAG 配置。

## 分阶段执行与停止条件

| 阶段 | 具体工作 | 能取得什么 | 不能保证什么 |
| --- | --- | --- | --- |
| A. 继续免拆机调查 | 沿曝光参数设置到取景/拍摄的调用链追踪；查工程日志生成条件；审阅现成 BLE/HTTP 实现；必要时经用户配合采集协议和正常取景数据 | 更可靠的地址、状态字段、参数是否实际应用、取景帧时间 | HTTP 取景不是 CPU/任务诊断；远程模式可能改变卡死条件；没有已知的内存读取命令 |
| B. 识别硬件 | 在用户接受拆机或由维修人员协助的条件下，取得主板正反面清晰照片、PCB 版本、芯片丝印和测试点位置；结合资料及测量识别信号 | 确定实际处理器、存储、调试信号候选和电平 | 照片不能单独证明某焊盘就是 UART/JTAG；此阶段不接未知电源、不刷写 |
| C. UART 被动采集 | 确定 TX/GND、IO 电平和波特率后，先只接收相机发送的数据，保存完整正常启动日志及自然出现异常时的日志 | 若生产固件启用了输出，可见初始化、错误码、断言或最后事件 | 可能无输出、输出被禁用、或只是蓝牙 HCI/子处理器通信；串口存在不等于有 shell、RAM 读取或任务诊断命令 |
| D. JTAG 调试 | 确定芯片与引脚、电平、复位、TAP/核心配置且接口可访问后，用支持目标的现成探针与 OpenOCD/GDB 等工具采集现场 | 支持的核心寄存器、栈和可访问内存；有机会把运行代码与候选对照 | 接口可能未引出或被锁；暂停会改变时序，外设/DMA未必同步停止；无法自动识别未知 RTOS 的全部任务 |
| E. 有证据的局部修改 | 验证装载映射与解码后，逐项定义预期变化；适用时先做范围受控的 RAM 验证，再考虑持久化固件 | 最小补丁与可重复的前后对照 | RAM 改动也需检查函数副作用，不等于无风险；写 Flash 前仍需确认完整备份及恢复途径 |

用户已明确选择“先只做不拆机的软件调查”。当前只执行阶段A；B–E中的硬件操作不属于本轮执行范围。没有向相机发命令、访问 SD、切换网络、安装硬件工具或发送厂家邮件。

## 针对两个目标，应该采什么

### 完全挂死与操作卡顿

卡死现场优先保留 PC/LR/SP/CPSR、对应栈和已确认的任务/等待对象；若存在多核心，需要识别哪些核心参与 UI/成像/镜头控制。把现场和反汇编关联，区分持续执行、等待消息/锁、外设等待等情况。**单次 PC 落在某个循环，不能独自证明死循环或根因。**

响应优化需要时间证据：从 UI 输入、参数应用、镜头应答到画面刷新的事件时间戳。若必须增加诊断，先确定合法输出/缓冲路径，控制频率并测量记录开销。同步写 SD 或大量串口打印本身可能制造卡顿。JTAG 暂停不能代替真实运行耗时测量。

不要求用户继续反复制造挂死；在采集链路就绪前，保留自然发生的现场即可。

### 曝光亮度预览

要连通四层证据：用户设置值 → 拍摄参数状态 → 取景传感器曝光/增益 → 显示补偿。确认拍照和取景分别读取哪些值，是否有自动亮度补偿，以及记录模式切换如何影响它们。

现有 `0xc1595420`、`0xc1469694+0x30e/+0x80` 仅是候选状态单元，含义未定，不能直接作为曝光开关写入。若能读取运行内存，先确认地址映射、MMU/缓存/别名及相关结构，再采集参数变化前后的值；不能把静态装载地址不加判断地当作 JTAG 物理地址。

真实内存中的未被运行时改写的代码片段，还可以用于对照独立解码候选，补足当前机身解压语义未验证的问题。

## 工具选择与资料依据

优先复用已有工具，不自写 CPU/协议栈或盲试未知命令：

- 静态继续用项目内 Ghidra/Capstone；Unicorn 适合已隔离的 CPU 指令路径，不能据此模拟完整相机 ISP、RTOS 和外设。
- 软件接口沿用 [bullbin 的 M1 协议实现](https://github.com/bullbin/xiaoyi_m1_re_liveview)。作者确认的是 3.2-int，本机 3.2-cn 兼容与调试能力仍须分别验证。
- UART 波形可由兼容电平的仪器采样后解码，波特率/帧格式应由信号确定，参考 [Saleae Async Serial 文档](https://www.saleae.com/support/protocol-analyzers/analyzer-user-guides/using-async-serial)。这不是指定购买某个型号。
- [OpenOCD ARM 架构文档](https://openocd.org/doc/html/Architecture-and-Core-Commands.html) 及 [通用寄存器/内存命令](https://openocd.org/doc/html/General-Commands.html) 说明相应能力；支持 ARM9 不等于已有 M1 主板配置。
- 探针信号必须符合目标 IO 电平；[SEGGER VTref 文档](https://kb.segger.com/VTref) 说明电平参考不是供电。尚未测定前，不假定本机为 3.3 V，也不照搬其他设备的针脚。

厂商提供的工程固件、符号表/MAP 文件、SDK/RTOS/成像接口资料，以及主板维修图纸，也是可并行寻找的捷径。来源和型号/版本对应关系需核实；当前没有取得这些材料，也未擅自联系任何人。

## 当前最具体的下一步

免拆机路线可以继续追踪调用链和日志条件；它可能取得进展，成功没有保证。若接受硬件路线，先做阶段 B 的主板识别，由此决定是否能进入 UART 采集。**先确认目标与信号，再选择转接板/探针；现在没有依据给出可直接照接的 M1 接线图。**
