## 结论摘要

1. **在候选 `.rodata` 中，没有找到任何一条可以支撑“某个具体卡死机制”的诊断字符串。** 本次扫描的候选 `.rodata`（3.2）中 `panic`、`watchdog`、`WDT`、`deadlock`、`stack overflow`、`reset reason`、`reboot` 字符串数量都是 **0**；“assert”只有 5 条，全部属于同一个 `../src/sha1_core.c` 断言块。字符串“不存在”只对本候选解码的这 3 个段有效，不能推广为固件绝对没有看门狗/panic 路径（DSP、RTOS 子系统、Wi-Fi 固件副本可能不在这些段内）。
2. **3.1 与 3.2 在这些高信号字符串上完全一致**：同样的字符串集合、同样的上下文，只随段长变化整体平移 +4/−4 字节（`.text` 内指针表平移 0x28 字节）。因此**现有证据不能支持“3.2 新增 assert / 新增内存耗尽检查 / 新增超时检查导致挂死”这一类假说**，也不能排除（因为没有任何一条字符串是 3.2 独有的）。
3. **没有发现“真正被调用”的断言/panic 处理路径证据。** 唯一确认被引用的诊断字符串只有 sha1 断言块，而它只被 `.text` 内部的一张**指针表**引用；在 ±4096 字节范围内（前、后两个方向）都没有找到加载该表槽位的 `ldr rX,[pc,#imm]`，也没有找到任何以该表基址为常量的取址指令。所以“字符串存在 + 有指针表”仍**不足以证明**该断言在运行期可达、更不足以证明它会打印后死循环。**不能判断**。
4. **“内存耗尽”和“总线超时”字符串全部属于 Broadcom Wi-Fi 驱动块（同区可见 `7.10.48.2 (r629111)`）**，不是主系统堆。把它们当作主程序堆耗尽证据是错误的。3.1/3.2 中这些字符串偏移与上下文逐字节相同。

## 三个最有价值的锚点（精确偏移）

证据分级：`S` = 仅字符串；`P` = 字符串 + 段内指针引用（数据表）；`C` = 已确认由指令直接取址（真正调用）。本次**没有任何锚点达到 C 级**。

### 锚点 A — sha1_core.c 断言块 + `.text` 内断言描述符表（等级 P，可达性未证）

`rodata` 偏移 / `va`（3.2），3.1 对应偏移为其 −4：

| rodata 偏移 | va | 内容 |
| ---: | ---: | --- |
| 0x4dad2c | 0x0091a52c | `assertion failed: W0 != NULL file %s, line %d\n` |
| 0x4dad70 | 0x0091a570 | `assertion failed: H0 != NULL file %s, line %d\n` |
| 0x4dadb4 | 0x0091a5b4 | `assertion failed: ctx != NULL file %s, line %d\n` |
| 0x4dadf8 | 0x0091a5f8 | `assertion failed: ctx != NULL file %s, line %d\n` |
| 0x4dae28 | 0x0091a628 | `assertion failed: digest != NULL file %s, line %d\n` |
| 0x4dae87 | 0x0091a687 | `syslogTask message receive failed.`（相邻，见下） |

引用侧（3.2 `.text`）：0x430bb4 = 0x0091a55c（`../src/sha1_core.c`）、0x430bb8 = 0x0091a52c、0x430bbc = 0x0091a570、0x430bc0 = 0x66666667（除法魔数，说明该区确实是编译器生成的常量/描述符池）、0x430bc4 = 0x0091a51c（指向二进制块，SHA1 常量形状）、0x430bc8 = 0x0091a5e4（`../src/sha1_core.c`）、0x430bcc = 0x0091a5b4、0x430bd4 = 0x0091a65c（`../src/sha1_core.c`）、0x430bd8 = 0x0091a628、0x430bdc = 0x0091a5f8。3.1 同构，整块位于 0x430b8c–0x430bb4（−0x28），指针值一律 +4。

- 每个断言点是一组 `{文件名指针, 格式串指针, 附加指针, 魔数, ...}`（步长约 0x14 字节），不是普通字面量池。
- 0x430bb0 处是函数收尾 `pop {r4-r7,r11,pc}`（`0xe8bd8cf0`），0x430be0 起恢复代码（`e3a02001` = `mov r2,#1`），说明该表是**函数体中间的内联数据块**。
- **未能确认消费方**：±4096B 双向扫描都没有 `ldr rX,[pc,#imm]` 直接指向这些槽位；也没有任何 32 位常量落在 0x430b80–0x430be8 区间（即没有“先取表基址再按下标索引”的写法）。若实现用 `add rX, pc, #imm`（ADR 风格）形成表基址，本次扫描不会命中——**所以“可达”与“不可达”都还没有证据**。

`syslogTask message receive failed.`（rodata+0x4dae87 / va 0x0091a687，3.1 为 +0x4dae8b）紧邻断言块，但 `.text`/`.rodata`/`.data` 中**没有**指向它的 4 字节指针（0 命中）。它可能是任务间消息接收失败打印，也可能是残字符串；**不能判断**是否与卡死相关，也无法把它接到任何任务或锁。

### 锚点 B — TRAP/异常打印格式串（等级 S，无任何引用命中）

`rodata` 偏移 0x0790fe / va 0x004b88fe，两个版本**同偏移、逐字节相同**，共 4 处重复：

```text
TRAP %x(%x): pc %x, lr %x, sp %x, cpsr %x, spsr %x
```

上下文：`FWID 01-%x`、`flags %x`、随后是 `  r0 …` 这类寄存器转储格式串（同区还有 `TCAM: %d used: %d exceed:%d`）。

- 这说明镜像里**存在**异常/中止转储的实现痕迹（寄存器 + pc/lr/sp/cpsr），但它是一条格式串，不是日志文件、不是可读取的崩溃记录。
- 在 `.text`、`.rodata`、`.data` 三段中对该字符串地址的 4 字节指针命中数均为 **0**（两个版本都是 0），即本次无法把它连到任何调用点。
- 因此：**不能判断**该转储在挂死时是否会执行、是否会写 SD、是否只走控制台/UART。它与 `reports/diagnostic-interface-investigation.md` 中“`SYSTEMERR`/`OS ERROR`/`STACK ERR` 只可能是屏幕/启动错误码”的结论一致，不构成新的可读诊断入口。

### 锚点 C — Wi-Fi 驱动块的内存/总线错误串（等级 S，归属已可辨，与主系统堆无关）

`rodata` 偏移（3.1/3.2 **完全相同**）：

| rodata 偏移 | va | 内容 | 邻接证据 |
| ---: | ---: | --- | --- |
| 0x078e9b | 0x004b869b | `reclaim section %s: Returned %d bytes to the heap` | 前有 `7.10.48.2 (r629111)`，后有 `Memor…` |
| 0x078f9d | 0x004b879d | `Malloc failure count: %d` | 前有 `…in use + overhead: %d(%dK), Max memory in use: %ld(%ldK)` |
| 0x07921a | 0x004b8a1a | `AXI timeout` | 前有 `busstats`、`AXI slave error`、后有 `AXI decode error`、`errlog: lo 0x%08x, hi 0x%08x` |

- 这三个字符串的地址在 `.text`/`.rodata`/`.data` 中**均无 4 字节指针命中**（0 命中），符合“由 Wi-Fi 固件内部的常量表/基址相对寻址使用”的形态。
- 归属依据：同区紧邻 `7.10.48.2 (r629111)`、`AXI slave error`、`busstats`、`errlog:`，与既有报告里 Broadcom 43430/7.10.48.2 的 Wi-Fi 调试区一致。
- 结论：**这些不是主程序堆耗尽或主系统总线超时的证据**；“Malloc failure count”“heap”出现在这里，不能用来支持“主系统内存耗尽导致挂死”。**不能判断**主程序是否存在堆耗尽检测。

## 明确不能判断的事项

- 完全挂死的具体机制（断言死循环、看门狗复位失败、互斥量死锁、堆耗尽、总线/存储超时、供电/热问题）：**不能判断**。候选字符串里没有任何一条能被证明在挂死路径上被执行。
- `TRAP` 转储是否执行、输出到哪：**不能判断**（无引用命中；UART 是否可接触在既有报告中仍未验证）。
- `syslogTask message receive failed.` 是否与卡死有关：**不能判断**（无指针命中）。
- 3.2 是否比 3.1 更容易挂死、以及用户报告的 5 次挂死与哪些代码路径相关：**不能判断**。不能据此删除任何功能或“优化”任何模块。

## 下一步所需的最少信息（不需要让用户制造挂死）

以下每一项都是**离线、只读**的，且都直接决定上面“不能判断”能否变成结论：

1. **断言/异常打印是否可达**：对 0x430b80–0x430c10 与 0x4b88f0 附近做一次 `add rX, pc, #imm`（ADR）风格的定点扫描，确认是否存在以 0x430bb4 或 0x4b88** 区为基址的取址。若命中，再看其后续是 `printf` 后 `while(1)`/`b .`（= 打印后死循环的一种可能路径，仍不能认定用户遇到的就是它），还是写文件/复位。这只能补充诊断消费方证据；即使发现死循环，也仍缺少它与用户挂死现场的关联，不能单凭该结果修改固件。
2. **0x4b8xxx 块的归属确认**：确认该块是主程序里链接进来的 Wi-Fi 驱动副本还是独立 Wi-Fi 固件段（用相邻的 `7.10.48.2 (r629111)`、`BRCM4`、`43430a1` 判据即可）。若确认属 Wi-Fi 驱动，则“堆/总线”证据只能用于 Wi-Fi 侧，主系统堆耗尽假说需另行取证。
3. **挂死现场的只读快照**（若将来自然发生，不要再主动复现）：屏幕错误码照片 + SD 根目录新增文件清单。这一步在 `reports/diagnostic-interface-investigation.md` 已列出，本次没有新增可执行入口，因此不改动其建议，也不建议通过创建 `.SDK` 文件去“打开日志”。

- 本报告没有提出、也不建议任何补丁；没有改动固件、`output/`、`scripts/`、`docs/`，只新增 `reports/freeze-static-audit.md`、`logs/freeze-static-audit.txt` 和 `temp/freeze-static-audit/` 下的脚本。未执行 git commit。
