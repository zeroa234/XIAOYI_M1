# 取景自动曝光（AE）代码定位

日期：2026-10-27。只读离线定位：Pi 子代理 `pa-0f8b7552` 分三轮查找，主代理逐条复核关键指令；未写补丁、未操作相机。输入为顺序复制语义的 3.2-cn 候选。标注：【主核】= 主代理用 Capstone 核对；【子核】= 子代理给出指令、主代理未逐条重看；【推断】。

目的：M 档改光圈/ISO/快门时取景亮度不变，为今后的"曝光预览"找接入点。**本阶段只定位，没有实现。**

## 结论

1. 档位编码已确定：设置结构 `0xc1401074+0xa9` 为拍摄档位（1 Auto、2 P、3 A、4 S、5 M），AE 内部模式 `+0xb7`（同时搬到 AE 控制块 `0xc1469694+0x4c`）为 P→2、A→3、S→4、**M→1**。
2. AE 每一步由 `0x362010` 驱动，核心算法是静态表 `0x86253c` 中 id==1 的 `0x365344`；结果以 APEX（Bv/Tv/Av/Sv）计算，输出 `ref`、曝光时间、光圈、感光度等，并发布到若干全局量。
3. M 档在 AE 里有专门分支 `0x36be00`，会把一个配置值直接写进工作曝光量 `ctrl+0x13c`，而 A/S 档走迭代。这个配置值的来源（`[0xc1401074+0x2c]`）还没确定是不是用户设定的快门或 ISO。
4. 显示侧（Y 曲线族）**不读**当前曝光量来调整亮度【子核·扫描】，所以取景亮度只能由相机端重算的曝光决定。
5. **把取景快门/增益写进传感器的那一步还没找到。** AE 模块本身不直接构造寄存器传输【子核·扫描】，施加大概在别的模块里，这是做曝光预览前最大的缺口。

## 1. 档位枚举【主核】

- 远程 JSON 的 `ExposureMode` 字符串表 `0x6b80fc` = `{Auto, P, A, S, M}`，在 `0x153038/0x153040` 按索引取用。
- `0x26590`：`ldrb r2,[0xc1401074+0xa9]`，经字节表 `0x5285b3` = `[0x0b,0,1,2,3,4,5,6,7]` 换成 JSON 索引，即 `+0xa9`：1 Auto、2 P、3 A、4 S、5 M。
- `0xad830`：`0x1b264` 读 `+0xa9`，以描述符 `0x531eb8`（键 `02 03 04 05 06 07 1c f7 fa`）二分查找后跳转：键 2→`+0xb7=2`、3→3、4→4、**5→1**、6→2；找不到键时不改。
- 【子核】`0x87f1c` 把 `+0xb7` 经 `0x354c1c` 写入 AE 控制块 `+0x4c`。
- 门控 `0x86914`：`ldrsb r0,[0xc1401074+0xb7]; cmp #1; cmpne #4; ldreq r0,[+0xc]; movne r0,#0`，即 **M 或 S 档才转发 `[+0xc]`**（S 和 M 都用用户快门，`[+0xc]` 被另处钳到 ≥250，可能与快门有关，未证）。

## 2. AE 步进与核心【主核】

```
00362018 ldr r4,=0xc159d7a0
00362024 bl  0x36eee8               ; 把控制块字段快照到 sp+8
00362084 bl  0x361ad4               ; 预计算 (sp+0x2f8, sp+8)
0036208c ldr r4,=0x86253c           ; .rodata 回调表 {id, fn} ×10
00362090 ldr r1,[r4,r0,lsl#3] / cmp r1,#1    ; 只取 id==1
0036209c bl  0x365c54               ; ip = fn, 栈参 {r5=0xc14708d0, r6=0xc14707e0}
003620a8 bl  0x30fd20               ; r0=1, r1=0（共享助手）
003620ac blx ip                     ; 0x365344(1, 0, sp+0x2f8, sp+0x2b0)
003620bc..003620f4                  ; 发布到 0xc146f4d8/4d4/4fc/4f8/500
00362100 str r0,[0xc1469694+0x118]  ; Ref
```

回调表：id8→0x3656e8、7→0x3657cc、6→0x3654d8、**1→0x365344**、5→0x3656a8、3→0x3655dc、4→0x365634、0/2→0x3648d0、9→0x365920。循环助手 `0x355a00` 为 `add r0,#1; cmp r0,#0xa`。子代理第一轮称此表"在 .bss、静态为空"，是漏看了 `0x36208c` 对 r4 的重新装载，已纠正。

AE 状态 `0xc14707e0`：`0x3652bc/c4/cc` 把一条输入记录的三个字写到 `+0x38/+0x3c/+0x40`（当前曝光三元组）；【子核】`0x3658b0..c0` 维护 `+0x44 + 12*i` 的历史。调试表头 `No,Bv,Tv,Av,Sv,AvND,irisID,StatusID,,Bv(x10),SS,Fno,ISO`（ADR `0x36a4fc`）和 `,Bv,…,ref,expTime,fno,sens,flash,caution,ev,shutter,fno,sens`（ADR `0x36a640`）说明内部以 APEX 计算、Bv 用 1/10 EV 定点。三元组各分量的单位尚未逐个确认。

## 3. 各档的目标计算【主核】

```
0036c4b8 ldr r0,=0xc1469694
0036c4bc ldr r1,[r0,#0x1ac] / str r1,[r0,#0x124]
0036c4c0 ldr r4,[r0,#0x4c]           ; AE 模式
0036c4c8 cmp r4,#3 -> A：0x36b978(1)
0036c4e8 cmp r4,#4 -> S：0x36c34c
0036c500 cmp r4,#1 -> M：0x35fc90(0)==0 ? 0x36be00(1) : 0x369d34(1)
```

- A：`0x36b984 ldr [+0x124]` → `0x35e208` 与 `+0x60` 合成 → `0x36b994 str [+0x128]`（Ref）。
- M：`0x36be90 ldr r0,[r4,#0x70]; 0x36be94 str r0,[r4,#0x13c]`。`ctrl+0x70` 由 `0x3544c8` 从 `[0xc1401074+0x2c]` 搬来【子核：搬运表】。`[+0x2c]` 有 5 个写者（0x2a6f0、0x33528、0xb1924、0xf37a8、0xf3fd8），语义未定。
- 【子核】录像采集 `0x358544` 把 `ctrl+0x13c/+0x144` 写回 `0xc146f4d4/4d8`。

## 4. 显示侧与施加

- `0x3d8de8`【主核】：读 `0xc146f4d8`，用 `ctrl+0x170` 写回，然后以 path 0x15 调 `0x3d8d10`（bank）和 `0x3d7fa0`（Y 曲线 provider 分派）。方向是"记录后选曲线"，不是"按曝光调亮度"。
- 【子核·扫描】Y 曲线族 `0x3d6f60/0x41e7d4/0x41ef2c` 不读 `0xc146f4d4/4d8` 和 `ctrl+0x118`。
- 【子核】`0xf880` 为 `mov r0,#0; bx lr`（主核：属实），使 `0x369d64` 必跳，`0x369d68–0x369e14` 中写 `0xc146f5ac` 的代码在这个版本里不会执行。
- 【子核·扫描】寄存器传输构造入口 `0x2af604` 有 178 个调用者，没有一个在 AE/显示区 0x340000–0x3b0000。传感器寄存器名（SHS/VMAX/HMAX）在全镜像中没有匹配。

## 5. 对早期报告的更正【子核】

`exposure-control-investigation.md` 用来支持"monitor/acquired 双状态 AE"的几条线索不成立：

- `MONITOR MODE:` / `MONITOR MODE(ACQUIRED):`（函数 0x39af84）是坏点统计按帧率模式分类的打印，邻近串为 `DEFECT DEFINITION:`、`-MONIT1 30FPS/…`。
- `MONIT_REC_MODE=`（0x396390）位于 `RAW_MODE=/RAW_SIM=/FLASH_TEST=` 调试设置回读块。
- `ACQLOOP AE`/`DEFOCUS AE`（函数 0x38dcd8）打印的是 `0xc1400444+0x1b9..0x1bc` 的 0/1 标志。

`BEF/AFT:SetMonit`（ADR `0x358980/0x358ab0`，函数 0x35894c）【主核】仍是取景相关线索。

## 6. 实测补充

`output/live-captures/20261026-081435-iso-probe-b53817` 的 75 个参数头中，M 档 ISO 100→200→100 期间 `EV` 始终为 `"5.0"`。所以 JSON 的 `EV` 不是"设定与测光之差"。【子核】它来自 `0x7d36c → 0x85d30` 读取的缓存 `0xc150f9f4`。

## 7. 设定 → AE 的推送链【主核】

```
00081470 add r0,sp,#0xc / bl 0xb7758     ; 由设置结构填 8 字 payload
00081480 bl 0x354b24                     ; thunk -> 0x35b678
0035b688..0035b6c4                       ; payload[0..7] -> ctrl +0x70 +0xa4 +0x4c +0x7c +0x58 +0x5c +0x48 +0x74
```

`0xb7758` 的取值：payload[0]=`src+0xc`、[1]=`src+0x14`、[2]=`(s8)src+0xb7`（AE 模式）、[3]=`byte[0xc140116c+0x16]`、[4]=`byte src+0xa0`、[5]=`src+0x1c`、[6]=`byte src+0xbf`、[7]=`src+0xb0`。`src` 由 outlined 助手 `0xb7aac` 给出，按 `+0xb7` 的用法推断为 `0xc1401074`。`0x354b24` 只有 `0x81480` 一个调用者，`0x81450` 又有 5 个调用者（`0x2881c、0x89a0c、0x8de80、0x9785c、0xb7330`），是公共的同步调用。

所以 M 档 `0x36be90/94` 写进 `ctrl+0x13c` 的 `ctrl+0x70`，来自设置结构 `+0xc`。`+0xc` 在 `0x124a94/0x124a9c` 被钳到 ≥250，形如快门微秒的下限（1/4000 s = 250 µs），这是推断，单位未证。

## 8. M 分支的完整顺序【主核】与一个待验证假设

`0x36be00`：先算 `+0x128`（`0x35e208`，同 A 档的 Ref），`+0x144 = 0x359e9c(+0x74)`，`+0x14c = 0x3595f0()`，`+0x130 = 0x35e2b4(+0x128, …, +0x14c)` 再经 `0x35e390(…, 100, +0x144)` 改写；`r5==1` 时 `+0x13c = +0x130`；`+0x140 = min(+0x13c, 0x3594c8())`；最后 `+0x13c = +0x70`。

**已排除的假设**：曾猜测 M 档快门取用户值、增益由 AE 自算来补偿亮度。核对 `0x3595f0` 后不成立【主核】：它先 `0x370d70`（`sub sp,#0x2a8`），再经 `0x36e8b8` 把控制块快照到栈上（`0x36e988 ldr [ctrl+0xa4] / 0x36e98c str [sp+0x58]`），最后 `ldr r0,[sp,#0x58]` 经 `0x35944c` 返回，即 **`+0x14c = ctrl+0xa4`，是设定值的原样搬运**。因此 M 档下 AE 的三个工作量 `+0x13c/+0x144/+0x14c` 都来自 `ctrl+0x70/+0x74/+0xa4`，也就是设置结构经 payload 送来的值。哪一项是快门、光圈、ISO 还没对上（JSON 的 `ISOSetting` 是按模式查表得到的档位，不能用来反推字段）。取景亮度不随设定变化的原因应在 AE 之外：显示/ISP 侧的亮度归一化，或另一套取景专用曝光量。

`0x352c38`【主核指令，归属存疑】：读 `[r4+0x13c]/[r4+0x140]` 当作 64 位曝光量，按 `floor(0x20000/(L−8))·(L−8)` 每帧拆分，经 `0x314ff4` 提交，再从总量中扣除，并把 r4 指针作为消息发给 ID `[0xc146f35c]`（`0x199874` 的第一个参数是 1..150 的消息 ID）。但在 AE 控制块里 `+0x13c` 和 `+0x140` 是两个独立字段（见上），所以这里的 r4 很可能是另一个对象（例如长曝光控制），**不能据此认定 AE 结果就是由它施加的**。

## 9. Ref 字段的读者与 SetMonit

- 【子核·扫描】`ctrl+0x118`（发布的 Ref）除 CSV 日志外没有读者；`+0x124`、`+0x128`、`+0x130` 的读者都在 AE 目标链内部。多轮扫描一致：这些字段的读者中，没有一个把它们送进寄存器传输（`0x2af604/0x2adbd8`）或消息（`0x199874`）。所以"把取景亮度拉回目标"的动作不在这些读者里。
- 【主核】`0x388550` 为 `ldr r4,=0xc1469694; mov r5,r0`，M 分支调用者传入 1，因此 `0x36be6c streq r0,[r4,#0x13c]` 总会执行，随后又被 `0x36be90/94` 用 `ctrl+0x70` 覆盖。
- 【主核】`0x3600b8`：当 `ctrl+3==1`、`+0x14c==+0x164`、`+0x144==+0x160`，且 `+0x130` 低于 `0x359318()` 的结果和 0x8235 时，调用 `0x366288(ctrl+0x384)`。形状像"曝光已到位后保持"，但不写传感器。
- 【主核】`SetMonit`（`0x35894c`）先快照 AE 状态，再依次调用 `0x3d8d04/0x358f18/0x3d8d0c/0x3d8d3c/0x3d913c/0x3d7fa0`（bank、Y 曲线 provider 与显示链），不写 ctrl 曝光字段。推断它是显示/监视模式设置，与取景曝光和增益无关。
- 【子核·推断】`0x35e2b4→0x35e248` 一带把比值换成 Q10 定点后分档；`0x35e390` 计算 `min(a, f(b))·b/c` 形式的比值。

## 下一步要找的

1. `[0xc1401074+0x2c]` 的含义：M 档写进工作曝光量的到底是用户快门/ISO，还是上一次 AE 的结果。
2. 取景曝光施加到传感器的路径：从 `0x2af604` 的调用者中筛出读取 AE 结果（`ctrl+0x13c/+0x144/+0x14c`、`0xc146f4d4/4d8`）的那些。
3. AE 调试 CSV 写入器 `0x35fcb8`（每 500 ms 轮换两个日志）的输出位置和开启条件。若能用现成的调试开关获得运行期 AE 数值，就有了不改固件的实测手段。
