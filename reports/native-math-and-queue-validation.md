# 原生曝光数值与消息发送：隔离执行验证

日期：2026-10-26。用户要求持续调查。使用已有Unicorn/Capstone/Ghidra，执行的程序字节来自原3.2-cn候选.text；数据对象和输入由测试装置提供。没有调用桩，没有相机、外设、真实调度或固件改写。

## 曝光数值的可复现公式

已连通实际机器码：`0x86898` 构建输入→`0x3544c8`→`0x36102c`→`0x360f4c`，之后把结果写到前述EV缓存。`0x3544c8` 的r4/r6由共享助手保存输入/输出指针，`0x36102c` 分别写输出+0x14和+0x18。

调用点明确使用当时sp+0x438为输入、sp+0x40c为输出，取sp+0x424（输出+0x18）的32位值传给 `0x85d30(1,value)`。另有一份strb镜像，但缓存访问器通过 `0x18b7c` 实际写32位，不能把这一条生产路径统一说成仅复制8位。

`0x360f4c` 的逻辑可表达为：

1. 从提供的有界表取上、下界。
2. 输入在区间内则差值为0；高于上界取输入−上界，低于下界取输入−下界。
3. 将差值/1024量化到最近的1/3，再以最接近的十分之一输出；中点向远离零的方向舍入。

这是显示EV的原生数值路径，但输入标量及界限的物理来源尚未全部确认，不能直接将它命名为“目标曝光−实际取景曝光”。`0x36102c` 从 `0xc159d74c` 读取有符号16位输入、从 `0xc1470010` 读取表；状态来自 `0xc1469694` 若干字段。

工具 `scripts/check-native-exposure-delta.py` 执行全部原生校验、表遍历、整数除法和返回路径，未替换任何调用。145项数值/边界用例、4项保护分支用例、145项完整生产函数用例通过；后145项运行 `0x36102c` 本身并核对结果及栈恢复。结果为 `native-exposure-delta-results.json`。

## 消息发送错误条件：纠正错误码和边界

完整执行 `0x199874`（包括真实中断屏蔽助手）确认：

| 条件 | 返回 |
| --- | ---: |
| ID不在1..150 | -18 |
| 注册表项+8为0 | -42 |
| 标志位2开启且节点+4非正数 | -17 |
| 本次测试中的有效、已建立对象和合法节点 | 0 |

`mvn #0x11` 为-18，`mvn #0x10` 为-17；`ID-1 >= 0x96` 即无效，不能把有效上界写成151。本函数未见返回-43的生产分支；共享错误尾支持-43，不代表此调用能生成-43。

`scripts/check-native-message-send.py` 在无等待任务、无调度的合成环境中通过11项返回条件及2项插入顺序验证：标志0为本次测试的FIFO，标志2按节点键升序且同键保持次序。没有执行真实任务竞争或证明队列容量/CPU性能。

## 队列对象与卡死判断的限制

发送包装的0x15是消息标签，内核队列ID实际读自对象首字。输入0x20c=524在包装中被放入节点+4，不能未经证据当作等待期限。

已找到队列句柄初始化写入：`0x26b4c` 将目标地址 `0xc14e1258` 装入r5，`0x26b60` 调用 `0x126c78(200,524)`，`0x26b64` 调用共享助手 `0x26e38`，助手执行 `str r0,[r5]`。之前只搜索直接str或普通调用约定会漏掉此写入。

这些事实继续支持“特定内核异常返回可以到达自旋”的局部机制，但削弱了“普通队列排满直接产生该错误”的说法。槽分配失败的路径与发送错误不同；正在继续核对生产者/消费者的锁与槽释放顺序。没有定位用户的实际卡死，不删除错误检查或吞掉消息。

## Gamma配置路径的新增区分

`0x2af604` 将地址、长度和后备位置编码为一个32位配置项并写入给定内存；它本身不是像素LUT写函数，也没有直接访问所编码的硬件地址。`0x2adbd8` 用它生成大量配置项，包含Gamma相关地址。`0x3d9294` 及共享助手则参与地址到后备位置的映射，尚在追真正的曲线数据写入者。

仍缺机身运行内存/现场对应、取景通道作用范围及可靠重打包；没有实现曝光模拟或性能修复。
