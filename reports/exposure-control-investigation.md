# YI M1 曝光预览控制：有限范围静态定位

日期：2026-10-26。对象：官方 3.2-cn 主程序。目标：在**不写补丁、不操作相机**的前提下，利用已下载的 echeetah 源码/静态资料和本地 3.2-cn 字符串，收窄“M 档、固定 ISO、闪光关闭时，成片随 ISO/光圈/快门改变，但照片与视频取景亮度不变”的控制路径。此现象已有用户受控复测描述，见 `observations-2026-10-26.json`；尚无独立的图像文件、元数据流或运行跟踪。

本报告没有修好任何东西，也没有声称已定位根因。所有固件偏移都是实验性解压文件的文件偏移；按已确认的节表，`.text` 的装载地址为 0x2000、`.rodata` 的装载地址为 0x43f800，但这不是已核实的运行期地址。字符串/调试标签只能作为线索。

## 结论摘要

现有证据支持一个**待验证的机制假设**，而不是已证实的根因：

> 取景预览走的是独立的 “monitor AE” 状态（连续/自动的监视曝光），拍摄或录像开始时才切到 “acquired” 状态，后者使用最终拍摄参数。M 档手动 ISO/快门/光圈被写入拍摄状态，但预览 monitor AE 没有跟随，所以取景亮度不变。

支持这个假设的本机静态线索：

1. `BEF:SetMonit` / `AFT:SetMonit` 两个调试标签夹着一段设置 monitor 状态的代码；候选函数起点在文件偏移 3501180（按 `.text` 基址折算虚拟 0x358c7c，仅为线索）。
2. 同一区域有独立的 `MONITOR MODE:` 与 `MONITOR MODE(ACQUIRED):` 标签，说明固件明确区分“监视模式”和“已获取/拍摄模式”。
3. AE 调试 CSV 表头同时有 `BvAcq/BvfMonit` 和 `RefAcq/RefMonit`，即采集值与监视值分开记录。
4. 另有 `LastMonit`、`AFT:monit_ae`、`ACQLOOP AE`、`DEFOCUS AE`、`MONIT_REC_MODE=`、`CamValue0.shutter_ref` 等 AE/monitor 状态标签。

但**没有**证明：

- 哪个调用点是实时取景；
- `SetMonit` 的参数如何选择 monitor/acquired；
- 预览不跟随手动曝光是 monitor AE 的正常设计、状态切换遗漏，还是其它 ISP/显示路径；
- 是否存在一个可安全修改的单一开关。

因此，本轮只把范围收窄到 “monitor/acquired 双状态 AE”，没有到达可打补丁的程度。

## 一、已有行为证据（二手，但来自实机测试）

`echeetah/yi-m1-monitor` 的 `fable research/live-testing-findings.md` 记录（3.2-int 实机）：

- 实时取景的 JSON 头同时包含照片/视频共用字段：`ExposureMode`、`ISOSetting`、`ShutterSpeed`、`Fnumber`、`EV`、`WB`、`ColorMode`、`MeteringMode`、`FocusMode`。
- 该文档明确记录：**录像开始前 live view 可能看起来仍是自动曝光；开始录像后，画面才变成实际裁剪和实际曝光**。这不是本项目的 3.2-cn 复测，但与本机用户观察方向一致。
- 同一文档的应用代码只负责显示/下载，不修改相机预览算法；`main_window.py` 中“live view now shows the actual crop & exposure”只是 UI 提示，不是相机修复。

这条行为证据把问题从“曝光参数没有写入”缩小到“预览路径与拍摄路径使用了不同的 AE 状态”。它不能证明所有固件版本、所有镜头都如此，也不能替代 3.2-cn 的受控复测。

## 三、收窄后的候选路径

目前可以把候选路径写成下面这样，但每一步都还需要验证：

```text
实时取景/录像状态机
  -> 选择 monitor 或 acquired 模式
  -> SetMonit 候选函数（文件 3501180 附近）
  -> monitor AE 参数（BvfMonit/RefMonit）
  -> 预览流
```

对照路径：

```text
拍照/录像开始
  -> acquired 模式（MONITOR MODE(ACQUIRED)）
  -> 拍摄参数（ISO/快门/光圈）
  -> 最终成片
```

“预览继续使用 monitor AE”是一种与用户观察相容的解释。现有文本线索不能证明取景一定停在该分支，也不能证明实时取景调用 `SetMonit`、其参数含义或它就是修补位置。

## 四、为什么现在不能写补丁

1. 没有符号表，函数边界和调用者未经过独立反汇编验证；字符串是内嵌调试标签，不等于函数名。
2. 解压器仍是实验性的；文件偏移不能直接当运行期地址或补丁地址。
3. `SetMonit` 可能同时被拍照、录像、回放、低功耗等多个路径调用；强行改一个分支可能破坏录像/拍照或引入新的挂死。
4. 已有用户在 3.2-cn 上的受控复测描述，但没有独立元数据/图像捕获来确认开始录像前后的全部状态变化，也没有确认监视 AE 的输入来自哪里。
5. 用户当前优先级是挂死与响应，曝光模拟排在后面；不应为了曝光补丁冒险改主程序。

## 五、下一步真正需要什么

### 1. 先做不写固件的受控验证（优先）

若后续进行一次有明确目的的观测，可接收 HTTP/UDP 实时取景元数据，记录以下字段在 M 档改 ISO/快门/光圈前后的变化。接收数据是读取行为，但配对及启动远程取景会改变相机工作模式，整段流程不能称为纯只读，也可能改变故障条件。当前未执行：

- `ExposureMode`、`ISOSetting`、`ShutterSpeed`、`Fnumber`、`EV`；
- 如果元数据里存在，记录 `Bv`/`Ref`/monitor 相关字段（具体字段名以实际 JSON 为准）。

同时记录取景画面亮度和最终照片/视频。目的不是修，而是确认：

- 相机内部状态是否真的变成手动值；
- 预览是否始终停在 monitor 值；
- 进入录像/半按/ AE-L 等状态时预览是否切换。

这能验证/否定“monitor vs acquired”假设，不需要制造挂死。

### 2. 再做一次静态调用图确认

在正确解码产物得到验证、并具备合适的 ARM 反汇编环境后，可参考 echeetah 的公开 Ghidra 步骤加载 `.text`/`.rodata`/`.data`。本项目尚未确认已有可用的 Ghidra 环境。分析目标为：

- 反编译文件偏移 3501180 附近函数，确认 `SetMonit` 的参数和写入的全局状态；
- 找它的调用者，判断哪个来自实时取景、哪个来自拍照/录像；
- 反编译 3773724 附近的 `MONITOR MODE`/`ACQUIRED` 打印函数，回溯状态变量；
- 确认 `BvfMonit`/`RefMonit` 与 `BvAcq`/`RefAcq` 的写入点。

如果确认预览路径固定使用 monitor 值，才讨论最小补丁；补丁仍必须离线验证、保留恢复路径，不能直接刷用户机。

### 3. 行为侧的最小对照

在不改固件的前提下，比较：

- 拍照前预览；
- 开始录像后的预览；
- 半按/ AE-L 后的预览；
- 回放/实时取景切换后的预览。

如果只有录像开始后预览跟随曝光，可把录像状态切换作为更强的调查线索；仍不能仅凭这一现象排除其他协同路径或确定唯一切换点。

## 六、边界声明

- 本报告没有修好曝光预览，也没有证明挂死与曝光路径有关。
- `SetMonit`、`MONITOR MODE`、`BvfMonit/RefMonit` 是**候选路径和状态证据**，不是已确认的根因或可补丁开关。
- 不建议把 Wi-Fi 预览 APP 的显示修改当作相机固件修复交付；APP 只能观察/显示，不能改变相机预览算法。
- 3.1 只作为对照/恢复备用；目标仍是保留 3.2 功能，先处理挂死与响应，再实现曝光模拟。
