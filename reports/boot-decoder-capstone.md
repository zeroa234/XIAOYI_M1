## 2. IPL 布局（有反汇编证据）

1. **`0x0000–0x3FFF` 是同一 4 KB 块的 4 份拷贝**：
   `sha256` 前缀 `9b80671870cb9656…`，在 `0x0000/0x1000/0x2000/0x3000` 完全相同。
   - `0x0000`：`e59ff018` ×5 + `eafffffe`，向量表；`0x20` 起目标 `0xfc/0x118/...`。
   - `0x0040`：`str lr,[sp,#-4]!`，读 `0xdbff`、`0x23000000`，`blx 0x526`。
   - `0x00FC`（reset）：`bl 0x130`（SDRAM 初始化）→ `0x100`：`msr cpsr_c,#0xdf`，`bl 0x1ac`（清零 `0x23c4` 字节 @ `0x2300d320`），`bl 0x24c/0x254`（空），`bl 0x40`（时钟），`b 0x114`（原地循环）。
   - `0x01AC–0x0248`：按 0x100/0x20/4/1 分块填零；不是拷贝/解码。
   - `0x0526`（Thumb）：访问 `0x21801000` 系列寄存器，`bl 0x3ea`；属硬件初始化，不是解码。
   结论：4 KB 启动块内**没有** LZSS 解码循环。
2. **`0x4000–0x11xxx` 是第二阶段代码/数据混合区**：
   - `0x4FF8`：后向逐字节拷贝；`0x5000–0x5034`：前向逐字节拷贝（见 §4）。
   - `0x5000–0x6000` 为完整 ARM 代码块（1024 条，10 push/11 bl/12 bx）；`0x6000–0x66E8`、`0x7000–0x7920`、`0x8000–0x8258` 为 ARM 函数区。
   - `0x8A8C/0x8AA0`：ARM；`0x8AA0` 访问 `0x300b2000`、`0x2300d45c`，像 NAND/DMA 初始化。
   - `0x8D78`（Thumb）：`push {r4,r5,r6,r7,lr}`，访问 `0x21801000`、`0x2300f6da`，属硬件/PCIe 类初始化。
   - `0xF668`：ARM 字符串/缓冲处理函数；`0x10000–0x10648`：`__udivsi3` 等 libgcc 例程。
   - `0x10980–0x111A3`：字符串/只读数据；`0x12000` 后全零。

## 3. 字符串 xref：未能解析（具体缺口）

目标字符串与偏移：
- `0x10AE0 "LoadData[ %-20s ] not found "`
- `0x110C8 "loading [%08lx:%8s] ...... "`
- `0x110F4 "Decode Error!"`
- `0x10A58 ".rodata"`，`0x10B5C ".ver_table"`

已做的检查（均为负结果）：
1. 全镜像按 4 字节扫描，无字面量等于 `0x10980/0x109E0/0x10AE0/0x10C8/0x10F4/0x110C8/0x110F4`；
2. 无 `0x2301xxxx`（把第二阶段加载到 `0x23000000` 的基址假设）形式字面量；
3. 无低 16 位为 `0x10F4` 的字面量（因此无 `base+0x10F4` 的绝对指针）；
4. 无 `MOVW/MOVT`、无 `add/sub rX,pc,#imm`（ADR）落在 `0x10600–0x12000`；
5. 无立即数 `0x10F4/0x10C8/0x10980` 的 `add/ldr` 偏移形式。

因此 `"Decode Error!"`/`"loading"` 的代码引用**无法用简单寻址解析**。加载器实际使用的是 RAM 中的名字表：`0x7EA8` 从 `0x2300d080` 取 3 项，`strcmp` 比较 `0x2300d0a4` 等 RAM 字符串；`0x793C` 从 `0x2300cff4` 取表项；文件系统分发经 `0x2300d1a0` 的函数指针（`0x4C28/0x4C4C/0x4C70/0x4C80/0x4C90/0x4CA0/0x4CC4`）。这些 RAM 字符串/指针表可能在启动时由别处复制/重定位，静态镜像中找不到直接指向 IPL rodata 的引用。

## 4. 逐字节拷贝助手：存在，但无调用者

- `0x4FF8`：后向逐字节：`ldrbne ip,[r1,#-1]! … strbne ip,[r3,#-1]!`。
- `0x5018`：前向逐字节：
  ```
  0x05018 ldrb ip,[r1],#1
  0x0501C subs r2,r2,#1
  0x05020 strbne ip,[r3],#1
  0x05024 ldrbne ip,[r1],#1
  0x05028 subsne r2,r2,#1
  0x0502C strb ip,[r3],#1
  0x05030 bne 0x5018
  ```
  若以 `r1 = out - distance`、`r3 = out` 调用，它**会**逐字节读取刚写出的输出，从而自然支持 overlap。
- 但对全镜像 `0x0–0x12000` 做 ARM/Thumb BL/BLX 目标扫描，`0x4FF8/0x5018/0x5038/0x506C` 的调用者为 **0**。它们在本镜像中未被执行路径引用（可能通过函数指针、被覆盖、或属未用库代码），**不能**作为解码器 overlap 的证据。

## 5. 修正上一阶段的错误标注

上一阶段报告把 `0xF580` 描述为 “memcpy 对齐/拷贝循环”，**这是错误的**。
Capstone 重新解码（`0xF580–0xF64C`）显示它是 **strcmp**：
- 逐字节比较：`ldrb r2,[r0],#1; ldrb r3,[r1],#1; cmp r2,#1; cmphs r2,r3; subne r0,r2,r3; bxne lr`；
- 之后按字比较（`ldr ip,[r2],#4; ldr r3,[r1],#4; cmp ip,r3`），返回字节差；
- 调用点 `0x7E34/0x7F64/0x7F88` 传入两个字符串指针并以 `cmp r0,#0` 判断相等。
之前把它当作“拷贝循环”的结论作废；它不是解码器。

## 6. 加载路径（部分定位）

- `0x7EA8`：保存参数，取 `0x2300d080` 的表项，`bl 0x10714`、`0x799c`，用 `0xF580`（strcmp）匹配 RAM 字符串，`bl 0x79C0` 处理块/页。
- `0x7C48`：按 `0x1400`/`0x1201` 分块计算，调用 `0x4CC4`（文件系统分发）和 `0x799C`。
- `0x8000`：上层更新/加载函数，调用 `0x6740/0x67F4/0x702C`(printf)/`0x6AB4/0x6B28/0x6E08/0x7EA8/0x7C48/0x10028`(div)。
- `0x793C`/`0x79C0`：名字表/块页计算，不是解码。

在上述函数中未见“读 flag 位 → literal/匹配 → 回填输出”的 LZSS 循环，也未见 `0x1000/0xFFF` 窗口常量（`0x1000` 立即数只出现在 `0x13C` SDRAM、`0x73CC`/`0x88C4`/`0x88DC`/`0x8954` 硬件配置）。

## 7. 结论与仍未证明

**已证明：**
- IPL 为原始未压缩 ARM/Thumb 代码；`0x0–0x3FFF` 为 4 份相同 4 KB 启动块。
- `0x5018` 存在前向逐字节拷贝循环，理论上可传播 overlap，但全镜像无调用者。
- `0xF580` 是 strcmp，不是 memcpy（修正）。
- 加载器部分路径（名字匹配、块/页计算、文件系统分发）已定位。
- `"Decode Error!"` 等字符串无静态直接 xref。

**未证明：**
- LZSS 解码 routine 的位置与调用关系；
- 匹配拷贝是否逐字节回填、是否允许 `distance < length`；
- 窗口 4096/min 3/max 18/flag 位序是否适用于本型号；
- vendor `lzss.js` 解压产物及 overlap 统计的真实性。

**当前缺口（不再扩展搜索，按要求收束）：**
1. 解码步骤可能在 IPL 之外（BOOT/ROM/硬件），或通过 RAM 函数指针调用，静态 xref 不可达；
2. 需要运行时 RAM 表（`0x2300d0xx`）的初始化来源，或设备 ROM/厂商源码；
3. `0x4000–0x4C00` 与 `0x9000–0xF000` 的代码/数据边界未完全递归展开（线性反汇编会停在数据处）。
