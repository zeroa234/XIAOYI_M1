更新说明：第 1–10 节保留首次停止记录；第 11 节起记录用户调整门禁、授权采用“保留官方 token＋局部字面量”方法后的继续工作。首次未生成固件的状态不代表后续构建结果。

日期：2026-10-27。**本轮未生成 roundtrip 或 canary 固件，未实现未经证实的重打包工具。** 已定位 IPL 的 FIRM 段表读取及硬件解码入口，并执行原始指令验证；原生解码验证未通过，依用户“验证不通过就如实停下报告原因，不要硬出固件”的约束停止构建。

## 2. FIRM 从哪里读取

**【指令核实 + Unicorn 执行验证】IPL 从 PTBL 查找 FIRM 描述符，不按待加载文件总长反推起点。**

- `0x4488–0x4494` 调用介质描述符的 `+0x18` 回调读 PTBL，随后 `0x449c → 0x683c` 检查 `@PEI` 魔数与条目数不大于 32。
- NAND 实现 `0x837c–0x839c` 向底层 Thumb NAND 函数 `0xd766` 传入 `(0, 0, 2, 目标地址)` 读取 PTBL；底层物理 NAND、坏块与地址转换没有仿真。
- `0x4144 → 0x7834` 选择分区；正常选择为 `0x10000012`（FIRM）。`0x4158 → 0x7ff8` 装载它。
- `0x8020 → 0x6740` 在 PTBL 中按分区 ID 查找，每项 24 字节。`0x67b8` 原样复制描述符；仅 PTBL 的版本字段 `+4` 为 0 时，`0x67c8–0x67e4` 才转换起始/长度单位。官方 PTBL 版本为 **1**，不走转换。
- 官方 FIRM 描述符为 `{0x10000012, 0, 1, 0, 0x10200, 0x23600}`。`0x8098–0x80a0` 读取其 `+8` 为 1，进入 `0x80fc → 0x7c48`。
- `0x7c64–0x7c9c` 取描述符 `+0x10` 的 **0x10200**，用回调读取 10 个 512 字节单位至 `0x40000000`。它不是扫描 SD 文件，也不读取 ASCII 容器头。`0x7c70` 取读位置时尚未引用任何压缩段长度。

使用官方 PTBL、原始首段及真正的 `0x7ff8/0x6740/0x7c48` 指令，NAND 回调桩记录到：

| 传给 NAND 回调的起始 | 数量 | 目标 | 首段内偏移 |
| --- | ---: | --- | --- |
| `0x10200` | 10 | `0x40000000` | `0` |
| `0x1020a` | 2 | `0x40001400` | `0x1400` |
| `0x1020c` | 4 | `0x40001800` | `0x1800` |
| `0x10210` | 4 | `0x43000000` | `0x2000` |
| `0x10214` | 6086 | `0x43000800` | `0x2800` |

此用例只把“从 FIRM 起始读取”映射到官方段体来验证表解析，**没有证明这些地址在真实 NAND 上的物理布局**。

### 与升级器长度公式的关系：必须修正旧推论

**【指令核实】主程序 VA `0x10f744–0x10f75c` 确实计算 `0xb000 - ceil(长度 / 0x20000) * 0x100`，但它位于命名段 `NPROG/NPG` 的段号 0 分派内。** 官方首头只列 `ND1 IPL PTBL`，没有 `NPROG/NPG`。

**【指令核实】官方无名首段的实际写入路径是主程序 VA `0x1100ac–0x1100dc → 0x10f644`，它通过 `0x69/0x66/0x64` 设备入口与 `0x10f46c` 写入。** 本轮未把其下层设备寻址与 IPL 的 PTBL 起始完整连通。因此，不能把上述命名段公式直接视为已证实的无名首段物理位置。

官方段长 `0x707800` 代入该公式得到 `0x7700`，与 IPL 回调读起始 `0x10200` 不相等；不能假定两者属于同一地址层或可以直接相减。也不能凭这个公式判断无名首段改变长度一定会移动。

**【推断】若后续获准构建，仍应首先保持正文总长、向量区、段表及各负载起点不变；压缩结果装不进原区间就停止。** 本轮没有因保持长度即可解决全部寻址问题而放行构建。

## 3. 装载表的真实结构与遍历

**【指令核实 + Unicorn 执行验证】段表是变长记录组成的链表，不是只凭字符串定位的平面数组。** 每条记录的前 24 字节为：

| 相对记录起点 | 字段 | 指令 |
| --- | --- | --- |
| `+0` | 下一记录指针 | `0x4c28–0x4c48` |
| `+4` | 名字指针 | `0x4c4c–0x4c6c` |
| `+8` | 地址 | `0x4c70–0x4c7c` |
| `+0xc` | 字节长度 | `0x4c80–0x4c8c` |
| `+0x10` | 标志 | `0x4c90–0x4c9c` |
| `+0x14` | 关联的目标记录指针 | `0x4ca0–0x4cc0` |

指针经 `0x4bd8` 转换：高四位为 0 时加 `0x40000000`，已为 4 时保留，其余变成 0。`0x4cc4–0x4d44` 遍历，`0x4d58` 最多比较 40 字节名字；`0x793c` 分别尝试偏移 `0x1000`、`0x40`，寻找 `.picbase` 以确定段表链。

`0x7cbc–0x7d34` 找 `.secinfo` 并用其长度决定还要读多少段表；`0x7d4c–0x7d78` 找 `.ROM.vector`、`.ROM.text`。随后从 `.ROM.text` 遍历到 `.codelimit`，每条调用 `0x79c0`（`0x7e44–0x7e70`）。这是 **ROM 记录链**，不能只按文件中三个压缩块的物理先后来解释。

| 记录 | ROM 地址 / 首段偏移 | 压缩字节数 | 关联目标地址 | 明文字节数 |
| --- | --- | ---: | --- | ---: |
| `.ROM.text` | `0x10002000` / `0x2000` | `0x2f910c` = 3,117,324 | `.text` `0x2000` | `0x43d438` = 4,445,240 |
| `.ROM.rodata` | `0x102fb800` / `0x2fb800` | `0x3eef74` = 4,124,532 | `.rodata` `0x43f800` | `0x570618` = 5,703,192 |
| `.ROM.data` | `0x106ea800` / `0x6ea800` | `0x1c819` = 116,761 | `.data` `0xc09b0000` | `0x52e50` = 339,536 |

**【指令核实】`0x79c0` 用 ROM 长度向上取整到 512 字节作为介质读取长度，并用关联目标记录的地址、长度设置解码输出。** `0x7a10–0x7a28` 根据 ROM 地址与 `.ROM.vector` 地址之差求起始介质位置；没有读取第三方拆包工具生成的元数据。

`0x7a38–0x7a60` 对标志 `& 0x30` 和源/目标长度作判断；压缩分支从 `0x7a90` 起，先读 0x800 字节至 `0x43000000`，调用硬件配置，接着读其余内容，最后等待完成。真实追踪第一个 `.text` 入口参数为 `(0x8, 0x43000000, 0x40002000, 0x43d438)`。

## 4. 解码本体在哪里、哪些参数仍然未知

**【指令核实 + Unicorn 执行验证】本条装载路径的解码由 MMIO 外设完成。IPL 没有在此路径里执行 LZSS token 解析循环。**

- `0x7b08 → 0x107ac` 参数依次为模式、压缩输入地址、输出地址、**明文长度**。
- `0x10714–0x10770` 配置 `0x30140000` 周边及相关时钟寄存器。
- `0x107c4` 取寄存器基址 `0x301402c0`；`0x107d4–0x1080c` 将源/目标减去 `0x40000000` 后分别右移 3、19 位写入地址寄存器。
- `0x10810–0x10824` 将明文长度高低部分写到 `0x301402e8/0x301402e4`。
- `0x10834–0x1083c` 写常量 **0xfee** 到 `0x3014031c`；随后还有 `0/4/0x5000/3` 的配置与重复写入，不能未经硬件文档就给每个寄存器命名。
- `0x108b4–0x108c0` 将模式 `| 2` 写入控制寄存器。
- `0x7b50 → 0x108d0`，`0x108d8–0x108e0` 轮询 `0x30140280` 的 **0x4000** 位，无指令计数或时间上限；完成后清状态、复位部分配置并返回。

**【推断】0xfee 与现有 LZSS 候选的初始环位置一致，是额外交叉证据；单个硬件配置常量不足以证明环大小、初值或 token 定义。**

仍未获得本型号原指令/真实硬件证明的项目：flag 位序及字面量标志、两个匹配字节的位域、绝对环位置还是相对距离、长度偏置及最大值、环大小及初值、初始可引用槽、重叠复制语义。现有第三方与顺序候选的结果只能作为假设及统计支持，不能在本报告升级成【指令核实】。

因此本轮不能满足“编码 token 格式完全按第 1 步核实”的前置条件。没有通过在 Unicorn 的 MMIO 回调里调用软件解码器来制造“原生解码通过”。

## 5. Unicorn 结果与调用桩

共 **10 个受限原指令用例通过其各自断言**：官方 FIRM 描述符 1 项，官方段表到硬件入口 1 项，三个压缩子段的硬件配置/等待 3 项，错误传播 2 项，外层 BOOT 回退 2 项，版本表复制 1 项。这与“原生解码通过”是两个不同结论。

| 子段 | 原生解码结果 | 与顺序候选逐字节比较 |
| --- | --- | --- |
| `.text` | 输出仍全部为预置 `0xa5`，停在 `0x108e0` | 未能进行，原生明文未产生 |
| `.rodata` | 同上 | 同上 |
| `.data` | 同上 | 同上 |

每个子段调用实际 `0x10714/0x107ac/0x108d0`，**没有调用桩**，记录 30 次 MMIO 写入；等待阶段各执行 1000 条指令后由宿主限制停止。输入、预期参考明文的长度与 SHA-256 均在 JSON 中；不能将未变化输出称为官方流本身解码失败。

完整装载路径用例替代 NAND 回调 `0x832c` 供数、打印 `0x702c`、三个计时器函数 `0x6ab4/0x6b28/0x6e08`；另跳过 `0x7b64` 的独立 BSS 清零 DMA。BSS DMA 使用 `0x30041000`，**不是上节 `0x30140000` 的解码外设**。所有表查找、偏移/长度计算、解码硬件配置仍执行官方指令。

错误与回退用例使用明确列入 JSON 的合成返回或无效 NAND 表，仅证明分支和错误传播，不证明真实 NAND 错误或 BOOT 的实际行为。

## 6. 校验、版本表与回退：旧结论需要收窄

**【指令核实 + Unicorn 执行验证】“Decode Error!” 不保证回退 BOOT。**

- `0x7c48` 找不到必要表项时返回 `-1`；`0x8104–0x8114` 检测到它，打印 `Decode Error!` 并设置 `r5=2`。
- 然而 `0x814c` 只用 `r5` 决定是否打印速度；`0x8184 mov r3,#0 → 0x8188 mov r0,r3` **无条件返回 0**。
- 用无效 NAND 装载表实际走 `0x7c48`，以及另一个向内部注入 `-1` 的用例，均观察到错误打印和最终返回 0。
- 进一步执行外层 `0x40cc`：内部 `0x7c48=-1` 时，只装载一次 FIRM，**没有 BOOT 回退**。另一个用例向外层明确返回 `LoadData=1`，才观察到 FIRM → BOOT 两次调用。
- `0x415c–0x4188` 的回退条件确实存在，但要求 **0x7ff8 的返回值非零**；本函数 `0x802c` 的 PTBL 描述符查找失败会返回 1，而上述内层解码错误会被吞掉。

**【指令核实】`Invalid Firmware?` 位于 `0x41b4`，受 `0x41a8 → 0x6740` 的 PTBL 描述符查找结果控制。** 它不是一个全面的固件 CRC 或签名验证函数；该分支返回错误 6。原指令硬件等待循环无软件超时，坏压缩数据是否完成、如何报告硬件错误仍未知，不能承诺会回退。

**【指令核实】`.secinfo` 在本路径用于链表及表大小；已核查的装载/解码路径没有对其末尾字作 CRC 比较。** 官方表末尾 `0x17a0` 有 `0x4e34f129`，含义及算法未确定。不能因看见这个字就认定 CRC，也不能据局部分析宣称整套启动链绝无其他校验。

**【指令核实 + Unicorn 执行验证】`.ver_table` 被定位后，`0x41d0 → 0x4b84` 把 IPL 自身运行地址 `0x23000000` 起 65 字节复制到传入地址。** 其作用在此是复制版本表，并非比较新旧主程序版本。独立执行 `0x4b84`、无调用桩，确认复制内容与长度以及返回值 65。

## 7. 首段独立写入已确认，省略引导段的依据

**【指令核实】主程序 VA `0x110048–0x110078` 循环处理包头列出的命名段。长度为 0 则跳过；循环结束后 `0x1100ac–0x1100dc` 总会尝试写无名首段，未受 ND1/IPL/PTBL 名字存在与否控制。** 因此结构上可以只保留主程序首段，省略三种命名段；不需要为触发首段写入而附带 IPL/PTBL。

主程序 VA `0x10f954–0x10fba8` 校验 SUM、`0x10f644–0x10f810` 写入分派及 `0x110000–0x11011c` 首段独立调用，均重新用 Capstone 核查。这些范围在快照/顺序两种既存明文候选间 **差异均为 0 字节**，避免把该局部结论建立在二者有争议的字节上；它仍不等于整个主程序已获原生解码验证。

本轮没有把“可以只列首段”进一步等同于“已构建、已被升级器接受、已在真实 NAND 正确写入”。

## 9. 刷写风险与恢复路径

- **【推断】**改版主程序若能进入固件信息/升级 UI，且这些路径未损坏，可由用户走官方 SD 流程刷回官方包。本轮未进行任何刷写或恢复实测。
- **【指令核实】**部分外层加载错误会让 IPL 从 FIRM 改载 BOOT；**内层段表/解码错误可能被吞掉**，解码等待也没有软件超时。不能把 BOOT 当成坏压缩镜像的可靠兜底。
- **未知：**BOOT 内容、实际 UI、触发按键、是否能刷机。官方包未提供 BOOT，离线无法确认。
- **未知：**硬件面对非法流的输出、错误/完成状态、看门狗处理；加载返回成功后主程序可能在 UI 前崩溃。此时仍无已证实的免拆机恢复手段。
- 即便未来只写首段、不写 IPL/PTBL，也只是保护引导代码，**不会自动保证可恢复**。

## 10. 继续构建前必须补齐的具体证据

至少需要取得该 SoC 解码外设的可信格式资料/独立硬件输出，或找到在同型号上可核实的软件实现，才能确认 token 位域、终止边界和复制语义。不能用一个基于现有候选算法编写的 MMIO 模型替代这项证据。

还需闭合 `0x10f644` 所用设备入口与 PTBL FIRM 地址的转换；确认真实版本页使用哪个字串。随后才有条件实现安全子集编码器、测试原区间容量、严格比较全部明文差异并产出两个受验证的构建。

本轮停止的直接原因是**原生解码与 token 真实性门禁尚未满足**；恢复路径的新发现进一步降低了贸然试刷的合理性。

## 11. 调整门禁后的前置事实核查

用户明确授权：不再以不存在的 SoC 解码外设仿真作为构建前提，改用“官方 token 保留＋受影响处字面量化”，并保留完整官方 ND1/IPL/PTBL 容器结构。本节起采用这一新门禁。

**【统计/结构证据】**flag 从最低位先处理，1 表示一个字面量字节，0 表示两个匹配字节。解析全部官方压缩字节后，重新分组序列化，三个子段均逐字节还原，包括最后 flag 未使用位与尾部。顺序解码与独立 ff7tools 的映射明文一致，快照解码复现原工具（包括它在环未满时的 warm-up 规则）。这些是结构与交叉验证，仍不是硬件 token 指令证明。

| 子段 | token 数 | 压缩字节 | 完整解码字节 | 映射字节 | 原 ROM 空余 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `.text` | 2,119,556 | 3,117,324 | 4,445,241 | 4,445,240 | `0x6f4` = 1,780 |
| `.rodata` | 3,240,392 | 4,124,532 | 5,703,192 | 5,703,192 | `0x8c` = 140 |
| `.data` | 79,802 | 116,761 | 339,537 | 339,536 | `0x7e7` = 2,023 |

特别更正一个长度细节：`.text/.data` 的完整压缩流各输出额外的一个 `ff`；只有按装载表长度截取的映射部分精确等于声明明文长度。实现保留完整 token 流与这两个尾字节，不用“输出长度恰好相等”替代实际数据。

### 11.1 `.secinfo` 末尾字扫描

`scripts/audit-secinfo-checksum.cjs` 同时核对两个官方输入及参考明文哈希，执行 3 个 CRC 已知答案自检。3.1-cn 对应字为 **0xe42cc312**，3.2-cn 为 **0x4e34f129**。

对每版的 22 个范围执行 **3,300** 次比较：首段整段、排除该字/置零、向量区、`.secinfo` 含尾字/排除/置零、4KB 段表及前 8KB、三个压缩正文、三个映射明文/完整明文、压缩与明文拼接等。算法包括 CRC32 IEEE、Castagnoli、Koopman、Q，正向/反射、初值 0/ffffffff、最终异或 0/ffffffff、输出反射和字节序；另有字节和、LE/BE 32 位字和及其补码/反码、Adler32 初值 0/1。

**【有限算法扫描】两版均未匹配。结论是“未识别”，不是“已证明不是校验值”。【指令核实】已核 IPL 装载路径不检查它。** 构建保留此字；压缩内容及明文版本字节改变后，它仍可能覆盖尚未识别的范围，这是剩余风险。结果见 `reports/secinfo-checksum-results-2026-10-27.json`。

### 11.2 三个版本副本和 HTTP 查询

- **0x834674【指令核实】**：唯一精确指针字位于主程序 `0x179118`，由 `0x17904c` 装载；`0x179054` 设置长度 7，`0x179058` 复制含 NUL 的版本串，`0x179068/0x179090` 分别调用文本测量/绘制。其函数内还显示另一器件的数字版本。未见此副本进入升级器或版本比较。
- **0x6b7f54【指令核实】**：精确指针字位于 `0x150b34`，`0x1509dc` 装载；`0x1509ec` 用 `Ver`、`%s: %s` 格式化，`0x1509fc/0x150a64` 调用文本测量/绘制。它是屏幕显示路径，不能称为遥控 JSON 版本返回路径。未见此副本进入升级校验。
- **0x61ce80【静态搜索】**：在 `.text/.rodata/.data` 中未发现指向此串或串内字节的显式指针；邻近已识别引用指向镜头名、音频资源、0x61ce87 的 `M1CN`。`0x14ee54–0x14ee5c` 的字符串比较读取的是 **M1CN**，不是前面的 `3.2-cn`；该型号字符串保持不变。未发现此版本副本被升级器/SD 文件名/包头 VER 比较使用。静态未找到引用不等于排除所有间接地址计算。

三处均纳入 `3.2-cn\0 → 3.2-cm\0` 同长补丁，仅修改 `n → m`，保留 NUL；完整清单位于 `config/canary-3.2cn.json`。现有证据没有触发用户要求排除的升级/版本比较用途。

**HTTP 调查的限制：未定位到返回这三个版本副本的 HTTP 命令，不能提供已验证的命令名。** 字符串/命令区可见 `GetCameraStatus` 等遥控入口，但未发现相应固件版本返回字段；`0x1509dc` 的引用本身是绘制，不是 HTTP 证据。本轮不连接网络，也不据此承诺刷后可用 Wi-Fi 验证。

## 12. 构建结果（主代理复核）

两份构建由 `scripts/repack.py` 生成、`scripts/verify-build.py` 验证，产物在被 Git 忽略的 `output/firmware-builds/`，manifest 与产物同目录。`tests/test-repack.py` 17 项通过（`logs/repack-token-tests-2026-10-27.txt`）。

| 构建 | SHA-256 | 与官方 3.2-cn 的差异 |
| --- | --- | --- |
| `roundtrip-3.2cn` | `92b3f1fda39e37351432d19d0167879f477eb71713a8fbc94b3ba2141ca404e4` | 无：与官方包逐字节相同，证明 token 解析/序列化无损 |
| `canary-3.2cn` | `b9eab77c9b459993e0d510d0afcb08dd136b836340b66b3bac7dbfbd465ad493` | 共 4 字节，见下 |

主代理用 `cmp -l` 独立比对 canary 与官方包，只有 4 个字节不同：

- 文件偏移 `0x36`：首头 `SUM=937552776` → `937552773`（三个 `n`→`m` 各减 1）。
- 文件偏移 `0x4101b5`、`0x47e976`、`0x5e7a8e`：`.rodata` 压缩流中的三个字面量字节 `0x6e`→`0x6d`。

三个 `n` 在官方压缩流里恰好都是字面量 token，且后续 4096 字节窗口内没有 token 引用这些环槽位（manifest：`replacedTokens=3`、`dependentTokens=0`、`growth=0`），所以是就地改字节：压缩流长度、flag 字节、段装载表、`.secinfo` 末尾字、ND1/IPL/PTBL 三段及其头全部不变。验证器在顺序复制与快照复制两种语义下解码，明文差异都恰好是 `.rodata` 0x61ce85、0x6b7f59、0x834679 三个字节。

证据等级：token 格式为【统计/结构证据】（官方流无损往返、两种独立解码器一致），不是硬件原生解码证明（`nativeDecodeVerified=false`）。canary 不改任何代码。刷写风险与恢复限制见第 9 节，仍然有效。
