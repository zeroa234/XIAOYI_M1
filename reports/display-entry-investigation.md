# 机身显示入口的本轮定位

日期：2026-10-26。目标是为曝光亮度模拟寻找机内接入位置。全程离线，沿用已有Ghidra、Capstone及候选映像；没有连接相机、改参数或修改固件。

## 当前结论

已找到带LCD设备描述关联的命令分派入口，以及一条上层成像配置到下层寄存器写入的实际调用链。尚未将两条链连通，未确认实时取景帧缓冲、可独立控制的取景增益/LUT或安全的曝光模拟接入点。

## 1. LCD设备命令入口

- `.rodata 0x83f578` 为 `INLX_30_103_LCD`。
- 初始化`.data`中的 `0xc09d0638` 指向这个名称；其偏移0x48的函数指针是 `0x2235b8`。另有 `0xc09d06e0` 同时引用这个名称及前一结构。这里有具体描述结构和回调关联，不仅是相邻字符串。
- `0x2235b8` 的实际指令按输入命令减1、检查范围，再用字节跳转表分派。可见分支转到 `0x223390` 等操作例程，以及 `0x223570`。
- `0x223570` 在 `0x223574` 直接装载 `0xc09d0638`，读取结构中的指针和输入索引（仅接受0或1），随后可能调用 `0x2088c4` 处理配置序列。

这些证据支持将 `0x2235b8` 称为LCD设备配置/控制命令候选入口。具体命令含义和配置序列尚未逐项恢复，未见足够证据把这里称为实时图像帧提交或曝光亮度处理函数。Ghidra在返回栈和跳转表处仍有未恢复部分，不能把伪代码中的额外间接调用都当作真实调用。

## 2. 从上层参数到成像硬件配置

已有路径 `0x81f04 → 0x81da4 → 0x355b38` 填写结构并写入成像状态。现进一步确认 `0x355b38` 经共享助手 `0x32240c` 将 r0设为输入模式、r1设为栈上配置结构，再调用 `0x3d7fa0`。

`0x3d7fa0` 的两处 `blx r3` 从初始化.data表 `0xc09e388c` 读取实际回调，表中7项依次为：

| 索引 | 处理函数 |
| --- | --- |
| 0 | 0x3d622c |
| 1 | 0x3d65f8 |
| 2 | 0x3d6750 |
| 3 | 0x3d6b28 |
| 4 | 0x3d7560 |
| 5 | 0x3d6f60 |
| 6 | 0x3d7a5c |

共享助手 `0x3bfe18` 的真实指令为递增r4、比较7、返回并保留标志位。输入模式1从索引1起，其他路径从0起，故反编译的条件无限循环不是可靠解释。此处尚未给各模式或7项处理程序赋予未经验证的业务名称。

其中 `0x3d6f60` 的下层调用包括 `0x420220`：后者实际读取输入结构，将值打包后写向 `0x30210fd8 + 实例偏移` 及后续两个字，确认已进入寄存器配置层。`0x41fbd4` 同样有向此类地址写入的指令。它们与LCD实时取景通路的关系仍待确认。

## 3. Gamma/亮度曲线线索的边界

内嵌寄存器转储描述含 `GAM_TOP GAMMA TABLE`（对应描述中的0x30115a24/0x30115a2c）及 `PST_TOP Y_GAMMA`（附近有0x30115bb0）。另两组代码/数据表也引用该区域。这确认存在有关处理块的固件描述，尚未证明可直接重写的像素LUT、增益单位、通道选择或实时取景可用性。

没有把Gamma文字、寄存器转储地址或LCD背光类控制当成已完成的曝光模拟入口。也没有通过这些地址访问真机硬件。

## 工具与可复核内容

配置清单：`config/display-candidate-targets.txt`、`config/display-dispatch-targets.txt`、`config/lcd-device-targets.txt`。Ghidra导出分别在 `output/display-candidates-3-2/`、`output/display-dispatch-3-2/`、`output/lcd-device-3-2/`；均记录候选节SHA-256。

用Capstone逐条核实4个共享助手（12/12/12/20字节），将其加入已有导出器的inline列表：`0x32240c`、`0x3564ac`、`0x3bfe18`、`0x3d6074`。更改只作用于分析数据库，未改变固件机器码。

剩余缺口：LCD命令与成像输出的连接、当前取景通道/缓冲所有权、取景曝光基准、控制增益/曲线的接口及作用范围。所有地址仍来自未经真机内存对照的候选映像，没有刷机补丁或性能修复。
