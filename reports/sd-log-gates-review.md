# SD 日志文件生成条件复核（AE_DBG.TXT / ESTEG*.DBG）

只做离线静态复核：未访问 E:、未连接相机、未发送任何设备命令、未新增 `.SDK`、未刷机、未改动主 Ghidra 数据库、未重新解压。输入是已有的候选视图
`output/reference-decoded/body-3-2-cn/{text,rodata,data}.mapped.candidate.bin`，装载基址按 `.text@0x2000`、`.rodata@0x43f800`、`.data@0xc09b0000`。
**该候选的解压语义仍未由真机验证**，因此下文地址一律视为“候选镜像内的虚拟地址”，不是已验证的机内地址。

方法：不做 C 级签名推断，只做字节级事实——字面量池定位（`.text` 内 4 字节字 == 目标 VA）、`ldr rX,[pc,#imm]` 解析、`add/sub pc` 型 ADR 扫描、全 `.text` 的 BL/B 目标反查、`.data` 指针扫描，再用 Capstone（5.0.9 发行包模块 5.0.7）反汇编引用点邻域。编译器 outline helper 会改动 r0/r1/SP，所以“谁调谁、参数是什么”只在能看到寄存器赋值链时才认定。

## 结论

1. **当前没有已验证的日志输出入口。** `AE_DBG  TXT` 的调用参数已进一步核对为句柄/通道 0x2c、文件名缓冲与零值；后续存在读取、数字解析及写参数字段的行为，更像调试参数输入。`ESTEG*.DBG` 的文件包装语义和触发条件仍待确认。
2. **`AE_DBG.TXT` 路径有明确门控值：`[0xc159d68c+4] == 0x2c308`。** 这是内部命令字/参数值，不是用户可见开关。
3. **`ESTEG*.DBG` 例程在本轮扫描中未找到直接调用者**：全 `.text` 无 B/BL 命中 `0xee84/0xee85`，`.text`/`.data` 中也没有值等于 `0xee84` 的 32 位字（函数指针表也无）。只能证明“代码存在且被一次性标志位保护”，不能证明它何时被执行。
4. **没有确认的安全入口，因此不提出任何触发文件方案。**

## 锚点 1：`AE_DBG  TXT` 的唯一代码引用与门控

- 字符串：`.rodata` 文件偏移 `0x421e25`（= 4333093，与旧记录一致）→ VA `0x861625`，字节为 `41 45 5f 44 42 47 20 20 54 58 54 00`，即 8.3 形式 `AE_DBG  TXT`（6 字符基名 + 2 个补齐空格 + 3 字符扩展名，无点），连 NUL 共 12 字节。
- 引用形式被重新确认：**`0x35f488` 不是指令地址，而是 `.text` 中的一个字面量池字**，值 `0x00861625`。旧报告“`.text` 虚拟地址 0x35f488 有引用”应更正为“0x35f488 是池字，真正的取用指令在 0x35f3f0”。
- 取用指令：`0x35f3f0: ldr r1,[pc,#0x90]` → 池 `0x35f488`；`0x35f3f8: bl 0x18cb90`（`mov r3,r0; cmp r2,#0; bxeq lr; tst r2,#3 …` = memcpy/strncpy 一类），入参 `r0=sp+0x84`、`r1=该文件名`、`r2=0xc`（12）。即：把 8.3 文件名拷进栈缓冲，**没有紧随 fopen/open 调用**。
- 门控：`0x35f3e8: ldr r4,[pc,#0x94]` → 池 `0x35f484`，值 `0xc159d68c`（RAM 结构基址）；
  - `0x35f3fc: ldr r0,[r4,#4]`；`0x35f400: ldr r1,[pc,#0x84]` → 池 `0x35f48c`，值 `0x0002c308`；
  - `0x35f404: cmp r0,r1`；`0x35f408: bne 0x35f4f8`（直接跳到 `b 0x585f8` 退出）。
  - 门控通过后：`0x35f41c: bl 0x18dad8`，入参 `r0=r4+0x20`、`r1=-1`、`r2=0x44`（68 = 17×4，把 AE 参数区清成 0xFF），随后 `0x35f424: bl 0x36005c`（该地址是“返回常量”helper：`mov r2,#0; mov r0,#0x2c; mov pc,lr`，返回 44，不是文件操作），`0x35f428: bl 0x13e00`（veneer → `b 0xf1ba4`），再 `bl 0x7cf98`，进入 `0x35f490` 起的 17 次数字解析循环（`0x35f4e8: cmp r4,#0x11`），结果写回 `[r5, r4, lsl #2]`，`r5 = 0xc159d68c+0x20`。
- 调用者：唯一 BL 调用点是 `0x35fc00: bl 0x35f3e0`（`0x35fc04: b 0x35fc38`）。其上下文把入参 `r5` 与 `0x2bf20`/`0x2c308`/`0x2c6f0`/`0x2cad8`/`0x2cfc0` 分档：`0x35fbf8: str r5,[r1,#4]`、`0x35fbfc: str r0,[r1,#0x14]`，`r1 = 0xc159d68c`。**因此内层门控只有在入参恰为 `0x2c308`（181000）时通过**；落在 `0x2bf20..0x2c6f0` 但不等值时，函数立刻退出。
- 消费方：`0x35f9d8` 处 `ldr ip,[pc,#0x188]`（→`0xc159d68c`）、`0x35f9dc: ldr r1,[pc,#0x1b8]`（→`0x2c308`）、`0x35f9e0: ldr r0,[ip,#4]`、`0x35f9e8: cmp r0,r1`、`0x35f9ec: bne 0x35fa58`；通过后把 `+0x20` 起的 8 个字段（每个先 `cmn r1,#1` 判 `!= -1`）搬到另一 RAM 结构 `0xc1469694` 的 `+0x4c/+0x50/+0xce/+0x60/+0x74/+0x70/+0xa4/+0x5c`。同一门控值出现两处，说明 `0x2c308` 是 AE 参数通道的命令码，而非文件名开关。

## 锚点 2：`ESTEG.DBG` / `ESTEG1..4.DBG` 的引用与“无调用者”

- 字符串组（`.rodata` VA）：`0x440322 "ESTEG   DBG"`、`0x44032e "ESTEG.DBG"`（偏移 `0xb2e`，与旧记录一致）、`0x440338 "ESTEG1  DBG"`、`0x44034c "ESTEG1.DBG"`、`0x440360/0x440374`（2）、`0x440388/0x44039c`（3）、`0x4403b0/0x4403c4`（4）。每项都成对出现：8.3 空格填充名 + 带点长名。
- 引用同样是池字：`0xf218 = 0x0044032e`、`0xf21c = 0x00440322`（旧记录“`.text` 0xf218 引用 `ESTEG.DBG`”应更正为池字）。
- 取用：`0xee98: ldr r1,[pc,#0x378]` → `0x44032e`；`0xee9c: ldr r0,[pc,#0x378]` → `0x440322`；`0xeea0: bl 0xedc8`。注意 r0/r1 的分配：r0 拿到 8.3 空格名，r1 拿到带点长名，与该 helper 在 `0xeed0` 的第二次调用方式一致（`r0 = sp+i*40`，`r1 = r0+0x14`）。
- 一次性门控：`0xee90: bl 0x30fd48`，该 helper 体为 `ldrb r0,[r4]; cmp r0,#0; mov pc,lr`；`0xee94: bne 0xeee4`（退出）。置位 helper `0x30fd54` 为 `mov r0,#1; strb r0,[r4]; mov pc,lr`。即：标志字节已置位则不再执行，首次执行时置 1。
- 门控通过后：`0xeeac: mov r2,#0xa0`、`0xeea4: cmp r0,#0`、`0xeea8: bne 0xeee4`（`0xedc8` 返回 0 视为成功）；`0xeeb0: ldr r1,[pc,#0x368]` → `0x440338`、`0x18db8c` 拷贝 0xa0 字节到栈；`0xeec4`–`0xeed8` 循环 `i=0..3`：`r0 = sp+i*40`、`r1 = sp+i*40+0x14`、`bl 0xedc8`，`bl 0xf2d4` 后 `blo` 继续。
- **调用链断点**：全 `.text` 扫描 BL（`(w>>24)==0xEB`）与 B（`0xEA`）后，没有任何目标等于 `0xee84/0xee85` 的分支；`.text` 与 `.data` 中也没有值等于 `0xee84/0xee85` 的 32 位字。`0xee84` 前一条是 `0xee80: pop {r4,r5,pc}`，即它是一段独立函数，当前候选里找不到入口。可能是间接调用/表驱动（未见证据），也可能是死代码，**未验证**。

## 锚点 3：`0xedc8` 是不是“打开文件”？——未确认

`0xedc8` 的返回约定（0 = 成功）和参数形态（8.3 名 + 长名两份）看起来像文件登记/打开包装，但体内部依次调用 `0x3fef9c`、`0xf3180`（`cmp r0,#0x16`）、`0x30fa3c`、`0x1aa70`、`0xe5214`、`0xe9b4`，并读取全局状态（`0x30000`/`0x70000` 分支），我**没有**在其中定位到带 mode 字符串（`"w"`/`"wb"`/`"a"`）的 open 调用点，`.rodata` 中 `"w"` 类单字符串过多（60+ 处），无法据此判定。**因此“`AE_DBG.TXT`/`ESTEG*.DBG` 会被真正创建”这一环仍未得到证据**，仅能说：文件名常量确实被代码取用，并以“名字对”的形式交给一个疑似文件层 helper。

## 未验证 / 限制

- 候选镜像未由真机验证解压语义；若解压错位，上述 VA 与指令划分全部失效。本次未重新解压、未改 Ghidra 数据库。
- outline helper 会改写 r0/r1/SP，文中“参数”只在能读到相邻寄存器赋值链时给出；`0x35f424` 调 `0x36005c` 属反例：该处是返回 44 的常量 helper，不能当作传参调用解释。
- `0xedc8` 的真实语义（是否 open、mode 为何）未确认；`0xee84` 的入口未确认。
- 没有运行任何设备侧操作，因此上述门控在实际固件里是否被触发、`0x2c308` 由哪条用户/内部命令产生，均未知。

## 对“挂死/曝光预览”定位的意义

本次核查只给出“日志文件名是常量、被 RAM 结构承载、受内部命令码门控”的静态事实，**不构成**可用于触发日志的诊断入口；`AE_DBG  TXT` 落在 AE 参数通道（与 17 个数值字段、`0xc1469694` AE 控制结构耦合），可作为继续追踪参数处理的线索，但尚未与曝光预览或用户挂死关联，但本报告不据此提出任何根因或触发文件。

## 主代理后续复核

`0x36005c` 是准备 `r0=0x2c,r2=0` 的共享助手，保留 r1 中的文件名；接着调用 `0xf1ba4` 包装。0x35f3e0 的后续循环读取最多17项，将数字解析结果写入参数字段，末尾调用 0xf1ef8(0x2c)。因此不能把 AE_DBG.TXT 当作已确认的诊断输出日志或建议用户创建该文件。没有找到 libc 风格 mode 字符串，也不能排除自定义文件层的打开操作。
