# 3.2-d1 无法开机：镜像原因审计

日期：2026-10-29。失败镜像 SHA-256：`6c247d53e127d0a3b3442f38b438afb15d24a7bb16fe51e6bf060fc635bc2b35`。本轮只读文件与局部原指令执行，未连接或操作相机、未生成新固件，原镜像及构建清单未改。

## 当前结论

**尚不能确认实机根因；最具体的候选是全量资源段重压缩引入了官方流没有的初始字典依赖。** 这不是普通的“音效太大”或已发现的容器 SUM 错误。已经确证的是：此前两个软件解码器共享同一个未经硬件验证的零初值假设，检查通过不足以放行该镜像。

这次为了替换快门声音，构建从保留官方 token 改成对整个 `.rodata` 使用通用 FF7 LZSS 压缩器。主代理没有证明新流的硬件兼容性，仍交付了 `firmware.bin`，随后又肯定确认用户按 SD 菜单升级。这是本次交付及验证决策的失误。文件检查通过或标为 experimental 不能消除这个缺口。

## 1. 新发现：第一条 token 读取尚未写入的字典

失败 RO 流的开头是 `fc ed ff ff fb ...`，`fc` 的最低位为 0，因此第一条是匹配 token `ed ff`：

| 参数 | 值 |
|---|---:|
| 当前输出位置 | 0 |
| 初始写指针 | `0xfee` |
| 引用字典槽 | `0xfed` |
| 距离 / 长度 | 1 / 18 |
| 对应的源输出位置 | **−1，尚无任何输出字节** |
| 预期明文 | 全零，之后继续引用，形成开头 32 个零 |

流在固件文件中的位置为 `.ROM.rodata` 首段偏移 `0x2fb800` 加 0x100 外层头，第一条 token 从文件偏移 `0x2fb901` 开始。原厂 RO 则先发出三个字面量零，再引用已经写入的零；两者对字典初值的要求不同。

复用现有 `firmware_tokens.parse_stream` 审计：

| 对照 | 未写入初始字典引用数 |
|---|---:|
| 官方 3.1-cn 的 text/rodata/data | 0 / 0 / 0 |
| 官方 3.2-cn 的 text/rodata/data | 0 / 0 / 0 |
| 此前用户报告能开机的旧曝光实验包 | 0 / 0 / 0 |
| 本次失败包 | 0 / **1** / 0 |

此前项目解码器用 `bytearray(4096)` 把初始字典全部置零；固定版 `ff7tools` 解码器把负的输出引用直接解释成零，压缩器也会预填零字典。这两种实现对本问题具有相同假设，不能相互独立地证明硬件初值。

## 2. 条件性复现，不冒充硬件结果

`scripts/audit-failed-demo-stream.py` 复用完全相同的项目解码器，只替换初始字典分配值，未新造编解码算法、未修改 token：

| 假设初始字典填充 | 官方 3.2 RO 相对零初值 | 失败 RO 相对零初值 |
|---|---:|---:|
| `0x20` | 0 字节变化 | **466 字节、367 段变化** |
| `0xa5` | 0 字节变化 | **466 字节、367 段变化** |

最早差异是 `0x43f800` 开始的 32 字节，随后传播到 RO 前部其他表项。原指令 `0x2394→0x239c` 会把这 32 字节复制到一个配置结构，但后续又覆盖部分字段；不能只凭这个引用就断言它必然导致启动失败。

**限定**：上述填充值是敏感性探针，不是测得的硬件初值。若真实硬件保证字典清零，这条 token 在这项语义上可以正确解码；若没有清零保证或不允许该引用，就可能得到错误数据或无法正常解码。IPL 配置寄存器中的复位/模式写入是否隐含清零字典，现有硬件资料没有回答。因此该候选仍不能升级为已确认根因，也不能据此承诺只改第一条 token 就可修好。

机器证据：`reports/failed-demo-stream-audit-2026-10-29.json`。两个官方版本、旧实验包及失败包的输入哈希、布局、token 统计、假设输出哈希均在其中。

## 3. 容器、段表和加载数量：未发现明确缺陷

`scripts/audit-failed-demo-loader.py` 复用既有 IPL 的 `Machine` 及原始未压缩 IPL，执行真实表链遍历。NAND 从文件供数；打印、计时、BSS DMA、解码配置及等待助手均明确列为桩，只验证参数与覆盖，不宣称实际解码成功。

- 四段容器的 SUM 与长度通过，完整文件 11,704,832 字节。向量块不变，ND1/IPL/PTBL 的头和内容逐字节不变。机内实际 NAND 是否写入完整，仍未读回验证。
- 段表只更改 `.ROM.text` 与 `.ROM.rodata` 的压缩长度；VA、关联记录、目标明文长度和标志未变。
- 失败 RO 的 4,050,675 字节压缩流被原加载器请求的 4,051,456 字节读取完整覆盖，没有因长度缩短而被截断。原流相应读取 4,125,184 字节。
- 原始 IPL 传给解码器的 RO 参数在两包中相同：`(8, 0x43000000, 0x4043f800, 0x570618)`；源、目标及明文长度的 8 字节对齐未变。压缩长度的奇数值本身不构成已发现的硬件长度错误。
- 未知表末尾字 `0x4e34f129` 保持原值；已核 IPL 装载路径未见对其进行 CRC 比较，不能把它认定为本次漏更新的 CRC，也不能排除更早阶段或未核路径的其他检查。
- 新旧流末尾 flag 形态不同，且新流后保留了一段旧压缩区内容。已证解码器配置采用目标明文长度，但硬件读取/终止语义尚未完整证明；这些作为未闭合项保留，未找到可独立确认的失败机制。

机器证据：`reports/failed-demo-loader-audit-2026-10-29.json`。

## 4. 曝光、声音与命令补丁：没有找到可确定的开机阻断

- 新 hook 与 104 字节包装器的原有 22 个局部用例通过；ABI 局部成立不等于整机启动验证。没有完成“屏幕出现前绝不会执行 AE 回调”的全程序证明，所以不能排除曝光改动的影响。
- 复用区属于函数 `0x369d50` 内的未执行分支体，**不是空白填充**。主代理额外用原生指令执行官方与失败包两种前置门控：未改的 `0xf880` 返回 0，`0x369d64` 均跳到 `0x369e18`，没有进入包装器区。此检查不排除未恢复的间接入口或运行期代码改写。
- 资源槽 `0x62102c..0x66777e` 正好容纳一份原始 WAV；新 WAV 在槽内，其余 8 个原资源字节保留，原最终镜像声音验证已通过。普通快门路由与开机音别名的静态识别不能替代真实播放验证，也不能穷尽音频引擎的长度计算规则。
- 命令表边界改动仍是远程命令处理路径，既有 106 个隔离用例没有发现异常；未发现其直接参与复位启动的证据。

机器证据：`reports/failed-demo-patch-gate-audit-2026-10-29.json`，并引用原有曝光/声音验证。pisub `<analysis-task>` 的初稿把 EV 单位说成 1/16、把冷启动不可达说得过强，并混用早期 WAV 大小；主代理要求纠正，这些未进入本报告结论。`<analysis-task>` 对 loader 的检查亦由主代理用正式脚本独立复现；“旧长度只出现一次”不能单独证明没有其他派生长度消费者。

## 5. 为什么当前表现可能是全黑且不回退

已有 IPL 指令与隔离验证表明，主程序开始前需加载这些压缩段；硬件完成等待没有软件超时，某些内层错误也不会向外层 BOOT 回退传播。若该阶段卡住，主程序提供的屏幕及 USB 功能不会启动。这个机制与当前现象相容，**并非已经定位到相机当时停住的指令**。OFF/ON 无充电灯同样不能单独证明主程序、IPL 或电源芯片哪一个坏了。

最终归因需要原生解压格式/初始状态的可信资料，或设备启动日志、读回内容。当前不具备这些证据。即使未来修正这项初值依赖，也必须继续保持 demo 撤回，不能再次以软件往返校验替代硬件兼容和恢复验证。

现成资料核查：[固定版 FF7 LZSS 实现](https://github.com/cebix/ff7tools/blob/6bf1fbcec2c88c1856cffd4a371719b406fee654/ff7/lzss.py)、[M1 原拆包工具](https://github.com/protyposis/yi-mirrorless-firmware-tools)。前者面向 FF7，并不声明 M1 兼容；后者也明确警告重打包压缩尚不完全正确。没有查到本型号解码外设的可核实初始化规范。此次自写部分仅是现有解析器、解码器与 Unicorn 的只读审计胶水。
