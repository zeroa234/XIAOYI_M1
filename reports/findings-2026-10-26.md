# 小蚁 M1 第一轮核实

日期：2026-10-26。机身：YI M1；镜头：12-40mm f/3.5-5.6。用户确认目前均为官方最新版。

已找回有原厂来源的 3.1-cn，完成 3.1/3.2 的离线校验和分段比较。尚未找到导致卡死的具体代码，也没有经过验证的定制更新；相机和 SD 卡未被刷写、格式化或改动配置。

## 已核实的事实

| 项目 | 证据与结论 | 不能由此推出的结论 |
| --- | --- | --- |
| 当前 3.2-cn 输入 | 用户 ZIP 与官网下载 ZIP 的 SHA-256 一致；机身程序为 C59Y1 / M1CN / Ver1.42 | 相机实际运行映像和内部存储已被完整验证 |
| 官方 3.1-cn | 从 2018-01-19 官网存档获取原始链接，经 HTTPS 从同一原厂服务器取回；发布说明为 2017-12-19；程序为 Ver1.41 | 3.1 在这台机身上一定更稳定，或已验证能降级 |
| 分段完整性 | 两版均有程序、ND1、IPL、PTBL 四段；四段的包内字节和校验均通过 | 这些简单校验是数字签名，或证明程序没有逻辑错误 |
| 版本差异 | 两版程序段均为 7,370,752 字节，内容不同；ND1（4,197,888）、IPL（131,072）、PTBL（4,096）三个段逐字节相同 | 程序段的差异具体导致卡死、性能下降或 AF 变化 |
| SD 卡检查 | Windows CHKDSK 只读检查最终报告未发现文件系统问题，退出码 0；原始日志开头还包含 Access is denied，保留完整日志供复核 | 完整坏块扫描、写速验证、卡或供电完全健康 |

当前 3.2 说明列出的变更是 iOS 11 预览问题修复；它没有列出具体性能退化，也没有详细代码改动清单。官方说明不能替代同条件真机回归测试。压缩流和编译布局的变化可导致大量相同偏移字节不同，不能把字节差异数量理解为修改代码量。

## 用户反馈的核实状态

1. **系统卡顿、完全挂死**：用户在本轮曝光调参测试期间报告挂死 5 次，并确认电源开关无效、必须拔电池恢复，多种操作都可能触发。将其记录为用户复现的严重系统无响应，稳定性优先于曝光预览增强；不再请求反复压力测试。尚无总操作次数、时长、最后一次操作类别或运行跟踪，因此不计算故障率，也不认定特定参数是唯一触发因素。多卡复现使固件成为合理调查主线；CPU 饱和、任务互等、资源泄漏或同步阻塞均没有日志/运行数据支持，暂不选择其中任一种作诊断。不能由论坛抱怨推定每一台 M1 都会以同一原因死机。
2. **新版比 3.1 更容易卡死**：用户的版本回忆，是可检验的回归假设。已找回对照输入，但未完成真机 A/B，因此尚未证实。
3. **模式切换时参数重置**：用户最新复测表示“好像有记忆”，因此撤回“当前机身参数普遍不保存”的初步假设，不再将其作为已确认故障或优先修复项。历史一手记录中，The Photography Forum 的用户在 3.0-int 上报告过开始录像将曝光补偿归零；这是另一版本的特定行为，不能代替本机复现。
4. **关机后忘记参数**：同样按用户最新复测调整为未确认；没有取得逐项、逐模式、正常重启的完整数值记录，不扩大为所有参数记忆均正常或均异常。
5. **预览不随曝光变化**：用户已确认 M 档、固定 ISO、闪光灯关闭条件；光圈、ISO、快门改变成片亮度，但照片取景和视频取景亮度均不随之变化，小蚁 12-40 与松下镜头上均复现。记录为本机经用户确认的跨镜头曝光预览问题，曝光参数的实际生效与预览失配已区分。未取得参数扫值、图像文件或单独的视频输出测量。Zack 的一手评测明确在 1.02-int/2.0-int 上报告曝光设定不改变取景亮度，支持这是长期存在过的机身侧行为。跨镜头相同提高机身预览控制这一方向的可信度，不能证明所有镜头都相同，也不能仅凭亮度不变确定底层原因。取景自动增益补偿是待验证的机制假设。官方指南未明确说明曝光模拟开关；当前检索和实验字符串检查也未发现已验证开关或现成修补，不能据此证明功能绝对不存在。
6. **AF 慢主要由算法导致**：官方历史更新确实列过 AF/AE 优化，证明软件可以影响表现；仅凭与松下的比较无法排除镜头驱动、传感器读取、处理资源和调参等影响，不能承诺仅改算法即可达到另一台相机的性能。

官方中文指南还明确区分 P/A/S/M 与全自动等模式的视频参数设置权限。相关权限表已渲染检查；它可以解释某些参数不可调的情况，不能用来否定用户报告的丢失现象。

补充历史一手证据：Imaging Resource 的 Field Test Part II 也报告更新后的 M1 会短暂无响应，偶尔完全挂死而需拔电池。可读检索正文没有给出明确版本，且文中尚无 RAW+JPEG，不能据此认定是 3.2 回归。它佐证类似严重挂死曾被其他实测者观察到，不能确定本机根因。直接打开本次返回 403；正文来自该原始评测的检索缓存。

## 目前的固件修改条件

- 现成工具 `protyposis/yi-mirrorless-firmware-tools` 固定于 `b90b96c124a3b076fa0283404e6595a4a40d20d0`。安装唯一锁定运行依赖 `string@3.3.3`，禁用安装脚本，所有文件和缓存留在本项目。
- 自写部分仅是 `scripts/unpack.cjs` 的分析适配，以及用标准库生成清单/比较记录；未自写压缩算法、AF 算法、相机固件补丁或刷机程序。
- 原工具未识别这两个 CN 版本。适配器仅在内存中加入已由官方包验证的型号、区域和 DVR 标识，并核对固定 SHA-256；没有篡改固件版本或字节。
- 两版离线拆包通过，原始输入的 SHA-256 保持不变。这证明分段可读，不证明解压后的全部代码正确。
- 调用原工具内置 `test` 验证 3.2 时，测试在重压缩回调中抛出 `TypeError: Cannot read properties of undefined (reading 'every')`，退出码 1。没有宣称压缩/解压往返验证成功。
- 比较的两个近期分支均未改动核心 `lzss.js`。2026 分支添加了测试回调防护和探测脚本，2025 分支添加文档及版本识别，不能当作已经修复的压缩器。
- 实验解压数据中出现部分可疑/破损文本。保存了少量持久化相关字符串线索，但许多属于无线配置或升级过程，**未识别出用户拍摄参数的保存函数**。字符串存在不能定位函数、证明 bug 或确定可修改地址。
- 社区有一条 2019 年用户反馈重打包 3.2 后能运行，作者也保留了工具风险说明；缺少可复核的测试包、区域和范围，不能据此认定当前 CN 版本可安全修改。

已取得上述用户复现描述。后续需要定位代码、建立可验证的解压/打包与恢复途径，再针对一项已定位行为修补。目前 USB 连接被系统识别为大容量存储，仅提供 SD 文件访问；本次没有相机内存、任务调度或崩溃日志可读接口，无法通过盘符直接验证运行时行为。

经用户授权，已启动两个 piagent 并行离线任务，分别审计压缩验证链路及诊断接口，均禁止接触设备或刷机。当前用户不需要继续制造挂死。

## 后续审计进展

- 用户重申以 3.2 为基线保留功能，并同时修复稳定性/响应和曝光预览；3.1 只作对照和恢复备用。
- piagent 独立复现了原工具测试器的匹配数组越界问题；编码/解码与逐字节回填语义存在可复现差异，但实际机身语义尚未得到原始启动代码证明，不能把条件性字节差异说成原厂固件损坏。详见 `codec-investigation.md`。
- 已用 Capstone 对原始未压缩 IPL 作实际反汇编，未在本轮范围内找到可证明格式的解码函数；第一阶段人工扫描中的错误解释已在对应报告更正。详见 `boot-decoder-capstone.md`。
- 复用未修改的 `cebix/ff7tools` 参考实现，按原厂未压缩节表的精确压缩长度和映射长度生成候选代码，保留全输出及额外 0/1 字节尾部。3 个解码向量、5 个小样本完整往返通过。它是独立的候选分析输入，不是经过机身验证的更新包。详见 `reference-decode-notes.md`。
- 基于候选代码的 Capstone 追踪发现，`MONITOR MODE`/`ACQUIRED` 标签主要用于模式枚举和诊断格式化，不能当作预览状态开关；`SetMonit` 标签也不能直接当作设置函数名。尚无最小可测的修改点。详见 `exposure-candidate-disassembly.md`。
- 当前挂死根因和曝光预览控制写入路径均未定位；继续准备反编译分析。没有生成、宣称完成或刷入定制修复固件。
