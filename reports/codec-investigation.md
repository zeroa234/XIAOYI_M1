# YI M1 固件压缩链路独立审计（离线）

日期：2026-10-26。范围：只审计 `scripts/unpack.cjs` 所依赖的第三方 LZSS 解压/压缩链路，以及原工具 `test` 的失败原因。未接触相机、未刷机、未重打包、未做区域转换、未修改任何固件字节。

主代理复核：测试器越界错误已独立复现。下文解码、编码和 5.12% 统计均以“逐字节回填的重叠复制”为参照；真机是否使用相同语义仍在由原始启动代码交叉核实。**不能把条件性差异说成原厂固件损坏，也不能仅凭通常的 LZSS 定义认定机身解码行为。** 未压缩装载/节表另含节长度，压缩流自身不带长度不代表整个容器没有长度信息。

## 结论摘要

这次 TypeError **不是固件错误**，也不是“压缩字节不同”本身。三类问题必须分开：

1. **测试器缺陷（已确证）**：`firmware.js:410-420` 用压缩器的第 n 个 lookup 去索引解压器的第 n 个 lookup，并默认两者一一对应。实际 3.2-cn 第一个压缩子段解压得到 732,823 个 lookup，重压缩得到 733,158 个；到第 732,824 个（1-based）压缩 lookup 时 `l1` 为 `undefined`，`.every` 抛 `TypeError`。测试在崩溃前打印的 50 条 “lookup mismatch” 是 lookup 数组差异，不能作为损坏证据；首条已核实两个 index 都指向同一目标。
2. **解压器与逐字节回填语义的差异（已复现，机身语义待证）**：`lzss.js:246-260` 先把整个 lookup 的 `length` 个字节预读进 `lookupBytes`，然后才逐个 append/write。遇到重叠匹配（`length > distance`）时，后半段读取的是尚未写入的 ring 槽位：ring 满时是 4096 字节前的旧字节，ring 未满时被 `readUInt8` 的 warm-up 公式映射到最旧字节。逐字节回填会允许本次匹配刚写出的字节作为后续源，与此输出不同。按该工具解析原始流，3.2-cn 后两个子段分别含 36,873 和 8,603 个这类匹配；是否符合真机格式不能仅由这一解析器证明。
3. **压缩器与逐字节回填语义的差异（已复现，机身语义待证）**：`lzss.js:70-96` 的 `find` 同样会检查尚未写入/旧 ring 槽位，因此可以发出 `length > distance` 的匹配。这种流能在同一实现下“往返成功”，但顺序复制解码会得到不同字节。压缩器还会用零字面量补齐最后一个 flag 组（`lzss.js:316-324`），造成 0–7 字节尾部长度差异。压缩流本身没有显式未压缩长度；外层装载/节表包含节长度，必须结合它确认边界。

对现有 3.2-cn 解压产物（三个压缩子段合计）做静态重叠一致性检查：至少 **536,608 / 10,487,988 字节（5.12%）** 与逐字节回填参照不一致（条件性下界，不是完整 corrected diff，更不是原厂固件损坏比例）。3.1-cn 为 **536,682 / 10,487,945（5.12%）**。全量重压缩 3.2-cn 三个子段得到 45,396 个与该参照不一致的重叠 lookup，涉及 533,860 字节。这些流能在原实现下完整前缀往返，但尚未独立证明符合机身格式。

因此：**现有 `output/body-*/*.decompressed` 不能当作已验证的正确反汇编输入；当前压缩器不能用于可信重打包。** 本审计没有产生 corrected image，也没有证明任何修改可启动或可安全刷写。

## 一、测试器缺陷：TypeError 是账本错误

`firmware.js:406-430` 的 `test` 逻辑：

```js
const recompressedData = lzss.compress(processedSectionData, {
  lookupCallback: lookupData => {
    compressionLookups.push(lookupData);
    const l1 = decompressionLookups[compressionLookups.length - 1];
    const l2 = compressionLookups[compressionLookups.length - 1];
    const similar = l1.every(function (u, i) { return u === l2[i]; });
```

`decompressionLookups` 由同一子段的解压回调填充，长度固定为 M；`compressionLookups` 在压缩过程中增长到 N。实测：

| 3.2-cn 子段 | 解压 lookup M | 重压缩 lookup N | N−M | 结果 |
| --- | ---: | ---: | ---: | --- |
| `0.00008192` | 732,823 | 733,158 | +335 | 第 732,824 个（1-based）压缩 lookup 的 `l1` 为 undefined |
| `0.03127296` | 479,090 | 481,170 | +2,080 | 尚未执行到；同样越界 |
| `0.07251968` | 26,983 | 27,384 | +401 | 尚未执行到；同样越界 |

原工具 `test` 在第一个子段就崩溃，因此后面的 DCD 字节比较根本没有运行。日志中压缩进度最后显示 100% 后才抛错；第 M+1 个压缩 token 已没有对应的解压 token，越界发生在压缩尾部，不是解压阶段。独立复现的命令与结果见上；栈顶仍是 `firmware.js:418` 的 `l1.every`。

日志在 50 条后只打印 “too many mismatches, stopping logging”，但 `similar` 仍对每个 token 计算，所以最终仍会 crash。崩溃前打印的首条 “mismatch” 为：

```text
lookup mismatch: 363,427,137,3,409 <-> 363,427,199,3,409
```

这里 `l1` 的 index=137、`l2` 的 index=199，但两者在当前 4096 字节 ring 中都指向同样三个字节 `d1 9f e5`，也就是目标 `out[427..429]`：

| 来源 | 物理 index | 对应输出位置 | 字节 |
| --- | ---: | ---: | --- |
| 解压 token | 137 | 155 | `d1 9f e5` |
| 压缩 token | 199 | 217 | `d1 9f e5` |
| 目标 `out[427..429]` | — | 427 | `d1 9f e5` |

所以这条 mismatch 只是“压缩器选择了另一个同样合法的匹配”，不是语义错误。压缩字节不同也不自动表示错误；真正需要验证的是解压后的字节和匹配的合法性。原测试的 lookup 逐项比较既不是字节比较，也不是独立的压缩器/解压器验证。

公开分支 `xiaobaiwud12/yi-mirrorless-firmware-tools` 的提交 `e682380` 曾把这里改成 `const similar = !!l1 && l1.every(...)`。这只会把 TypeError 变成“继续跑并打印更多 mismatch”，不会修复上述 1:1 假设；之后仍会用同一个有缺陷的解压器做 DCD，可能得到假通过。本审计没有采用该修改。

## 二、解压器缺陷：重叠匹配被预读和 warm-up 映射破坏

### 格式与预期语义

- 每个 flag 字节 8 位，LSB 优先；1 = 直接复制一个字节，0 = 一个 2 字节 lookup。
- lookup：`index = b1 | ((b2 & 0xF0) << 4)`（12 位），`length = (b2 & 0x0F) + 3`（3..18）。
- index 是 4096 字节 ring 中的物理槽位；ring 写指针从 `4096-18 = 4078` 开始（`lzss.js:17-20`、`decompress`/`compress` 的构造参数）。
- 正确复制必须逐字节进行：先复制 `index` 处字节，append/write 后再复制下一字节；当 `length > distance` 时，后续源可以是本次匹配刚写出的字节。这就是 LZSS 的重叠/游程匹配。

### 直接证据：真实固件流的第一个重叠 token

3.2-cn 子段 `0.00008192` 的第 21 个 lookup（0-based）：

```text
compressedOffset=134, outputOffset=146, index=124, length=14,
ringIndex=128, distance=4
```

上游解码输出（`output/...decompressed`）：

```text
a0 e1 00 00 d1 f0 21 e3 28 d1 9f e5 d2 f0
```

按逐字节重叠复制，前 4 字节 `a0 e1 00 00` 是已写入的源，后续应重复这 4 字节：

```text
a0 e1 00 00 a0 e1 00 00 a0 e1 00 00 a0 e1
```

把这段放回 0x90 附近：

| 偏移 | 上游输出 | 逐字节重叠输出 |
| ---: | --- | --- |
| 0x90 | `00 00 a0 e1` | `00 00 a0 e1` |
| 0x94 | `00 00 d1 f0`（无效 ARM 字） | `00 00 a0 e1` |
| 0x98 | `21 e3 28 d1`（无效 ARM 字） | `00 00 a0 e1` |
| 0x9c | `9f e5 d2 f0`（无效 ARM 字） | `00 00 a0 e1` |
| 0xa0 | `f0 43 2d e9`（`push {r4-r9,lr}`） | `f0 43 2d e9` |

逐字节版本在 0x90–0x9f 形成四个 ARM NOP，上游版本对应字节不同；两种输出的长度相同，不能据此声称发生字节对齐变化。NOP 形态支持继续检查逐字节复制假设，但没有证明这段字节一定作为指令执行，也没有替代原始启动解码器的验证。

### 合成向量（只解压，不写新算法）

| 向量 | 构造 | 上游输出 | 逐字节输出 | 首个差异 |
| --- | --- | --- | --- | ---: |
| warm-up 重叠 | 8 个字面量 `WXYZABCD`，lookup index=4082, len=8, distance=4，再 7 个 `Q` | `WXYZABCDABCDWXYZQQQQQQQ` | `WXYZABCDABCDABCDQQQQQQQ` | 12 |
| ring 满后重叠 | 4096 个字面量，前 4095 个 `A`、最后 `B`；lookup index=4077, len=18, distance=1，再 7 个 `Q` | 最后 `B` 后为 `B` + 17×`A` | 18×`B` | 4097 |

第一个向量说明：warm-up 阶段 `readUInt8` 把尚未写入的槽位映射到最旧字节（`WXYZ`），而上游预读使整个匹配在写入前完成；第二个向量说明：ring 满后预读拿到的是 4096 字节前的旧字节（`A`），不是刚写入的 `B`。两者都不是合法的顺序复制。

## 三、压缩器缺陷：无效重叠、尾部补零、极小输入缓冲区

### 1. 压缩器会发出无效重叠

`find` 对候选源 `searchIndex` 逐字节比较 `(searchIndex+y) % 4096`。当 `length > distance` 时，其中一部分 `y` 指向写指针之后的槽位：ring 满时是旧数据，未满时被 `readUInt8` 映射到最旧数据。它没有模拟“刚写出的字节”，所以可以把这些槽位误当作匹配。

最小反例（可直接用现有 `compress` 复现）：

```text
input = WXYZABCABCWXYZ   (14 bytes)
token = inOff 7, index 4082, length 7, ringIndex 4085, distance 3
input 源段 = ABCWXYZ
逐字节重叠应为 ABCABCA（周期 3）
```

压缩结果 10 字节；上游 `decompress` 得到 14/14 字节完整前缀，因此“解压→压缩→解压”看起来通过。但按顺序复制，输出应为：

```text
WXYZABCABCABCA
```

与输入在位置 10 开始不同（`W` vs `A`，共 4 字节）。这正是“同一对 bug 互相抵消”的假通过：压缩器按有缺陷解压器的读法编码，解压器再按同一读法还原。

### 2. 全量实测：当前产物重压缩后仍有大量无效重叠

输入是现有的 `output/body-3-2-cn/*.decompressed`（已说明其本身受解压器缺陷影响）。每个子段完整 `compress`，收集全部 lookup，检查 `length > distance` 时输入是否满足周期 `distance`。

| 3.2-cn 子段 | 输入字节 | 重压缩字节 | lookup | 重叠 lookup | 无效重叠 token | 无效重叠字节 | 上游 DCD 前缀 | 尾部多出 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| `0.00008192` | 4,445,245 | 3,116,106 | 733,158 | 403 | 379 | 1,967 | 4,445,245/4,445,245 | 1×0x00 |
| `0.03127296` | 5,703,200 | 4,122,489 | 481,170 | 36,871 | 36,611 | 437,859 | 5,703,200/5,703,200 | 2×0x00 |
| `0.07251968` | 339,543 | 115,953 | 27,384 | 8,538 | 8,406 | 94,034 | 339,543/339,543 | 2×0x00 |
| **合计** | **10,487,988** | — | — | **45,812** | **45,396** | **533,860** | 全部完整 | **5 字节零** |

解释：

- 上游 DCD 前缀完整，只多出 1–2 个零字节；如果只看“data match”或前缀比较，会误以为成功。
- 但 45,396 个重叠 token 在顺序复制语义下不成立；这些流不是相机格式的可靠编码。相机要能运行原厂流，其解码器必须支持重叠；上游解码器不支持，所以不能用上游 DCD 代表相机行为。
- 重压缩字节数比原始压缩子段小（原始含 2048 padding；重压缩未 padding），大小不是正确性证据。

### 3. 尾部补零与无长度字段

`compress` 在输入耗尽但 flag 组未满时执行：

```js
while (flags.length < 8) {
    flags.push(true);
    outputBuffer.push(0);
}
```

即用“复制零字节”补满 8 个 flag。`decompress` 会把这些零当作真实数据输出，因此：

- 小向量：7 字节 → 8 字节（+1 零）；9 字节 → 16 字节（+7 零）；`ABC`×20=60 字节 → 67 字节（+7 零）；100 个零 → 107 字节（+7 零）；255 字节序列 → 256 字节（+1 零）；1024 随机字节 → 1025 字节（+1 零）。
- 真实子段：4,445,245 → 4,445,246（+1 零）；5,703,200 → 5,703,202（+2 零）；339,543 → 339,545（+2 零）。
- 所有多出的字节都是 0x00，前缀完整。

压缩流自身不带显式未压缩长度，但外层装载/节表确有节长度。按当前解析规则，原厂流的每个压缩子段最后一个组都是完整 8 个符号（3.2 三个子段均为 `CCCCCCCC`；3.1 的 `0.07251968` 为 `LCCCCCCC`）；当前压缩器会用零字面量补齐组。如何按装载节长度正确处理尾部、以及机身如何停止解码，均须独立核实，不能把当前工具的零填充启发式当作机身算法。

### 4. 极小输入的固定 2× 输出缓冲区

`compress` 分配 `Buffer.alloc(buffer.length * 2)`（`lzss.js:277`），但极小输入的压缩结果至少是一个 flag 字节加 8 个数据字节：

| 输入字节 | `compress` 结果 |
| ---: | --- |
| 1 | `Output buffer is full, cannot write more data` |
| 2 | 同上 |
| 3 | 同上 |
| 4 | 同上 |
| 5 | 9 字节 |

这不是当前固件子段（数 MB）的问题，但说明压缩器对“最坏情况”上界假设不成立；作为通用工具是缺陷。

### 5. “压缩字节不同”不是错误判据

前面首条 mismatch 已说明：index 137 和 199 都是合法源。全量重压缩的压缩字节数与原始不同，但上游前缀 DCD 完整；仅凭字节差异或大小差异不能判定语义错误。必须检查解压后的字节和重叠匹配的合法性。反过来，上游 DCD 完整也不能判定正确，因为压缩器和解压器共享同一缺陷。

## 四、padding、长度和终止判定

1. **索引语义**：物理 ring index（初始写指针 4078），不是“从当前位置向后的距离”。证据：几十万个非重叠 lookup 按物理 index 取源全部匹配（`nonOverlapSourceMismatch=0`）；首条 mismatch 的两个 index 137/199 都指向同一目标。
2. **解压终止**：`lzss.js:191-209` 在 flag=0x00 且随后 16 字节全零时停止。实际 3.2-cn 三个压缩子段的停止位置分别为 `3117328`、`4124540`、`116767`，到子段末尾分别有 `1776`、`132`、`2017` 个零字节，均正好补到 2048 块边界；3.1-cn 同样通过。没有观察到真实流被提前截断。
3. **终止歧义**：如果合法的 8 个 lookup 恰好编码为 index=0、length=3（16 个零字节），也会匹配“结束”模式。合成向量：4096 个零字面量后接 flag=0x00 + 16 个零，上游只输出 4096 字节；若按 8×3 字节解码应为 4120 字节。实际 3.1/3.2 流没有触发，但这是无显式长度导致的潜在风险。
4. **压缩终止**：当前压缩器用零字面量补齐部分组；原厂流用完整 flag 组。DCD 的长度差是 0–7 个零字节，不是截断；但“忽略长度差、只看 min 长度 data match”的做法会掩盖它。原测试在崩溃前没有走到这里；即使修掉 TypeError，也会打印 `lengths do not match`，随后 `data match`，不能据此判定可重打包。
5. **重打包边界**：本审计没有运行 `repack`/`flipRegion`。`repack` 会把压缩子段补到 2048 并更新 section LENGTH/SUM，但不会改变上述无效重叠和尾部补零；它也不会验证相机端长度/偏移/签名。不能在未验证的情况下把“文件能生成”当作可刷写。
6. **输出缓冲区**：解压器分配 `input*10`；合法流的最大展开约为 `8×18/(1+16)=8.47×`，因此对合法流足够，本审计未观察到解压 buffer-full。压缩器的 `input*2` 缓冲区在 1–4 字节输入上会失败，见第三节。

## 五、对现有分析产物的影响

- 六个 `.decompressed` 产物都与本驱动重新解码的结果逐字节一致；因此它们是“当前工具的真实输出”，但不是“已验证的固件内容”。
